## Prompt Label

first-prompt

Ansible and Terraform are both used for Infrastructure as Code (IaC) to replace manual “ClickOps” with repeatable, auditable workflows defined in code.

- **Ansible (agentless automation + configuration)**: Ansible runs from a **control node** and connects to managed nodes primarily over **SSH**, pushing small modules to execute without requiring agents on the targets. Playbooks are written in **YAML** and typically use **idempotent modules**, so re-running them converges systems back to the desired state and helps reduce configuration drift. Ansible commonly supports **mutable infrastructure** (changing existing systems in place), which can increase drift over time; drift can be mitigated through **periodic playbook execution** and monitoring. A shown AWS example provisions a full web stack (VPC, security groups, EC2 instances, ALB) and then deploys **Nginx** consistently across environments. The tutorial notes control node prerequisites of a UNIX-like machine with Python plus **Python 3.8+** and **Ansible 2.14+**. An example playbook snippet (including use of **AWS Systems Manager (SSM)** for instances in private subnets) is:

```yaml
--- - name: Deploy Web Application hosts: localhost connection: local gather_facts: false pre_tasks: - name: Display deployment information ansible.builtin.debug: msg: - " " - "Web Application Deployment Playbook" - " " - "This playbook will:" - " - Install Nginx on EC2 instances" - " - Deploy custom web application" - " - Configure and start services" - "" - "Note: Instances are in private subnets" - "Connection method: AWS Systems Manager (SSM)" - " " - name: Refresh dynamic inventory ansible.builtin.meta: refresh_inventory - name: Configure web servers hosts: role_webserver gather_facts: true vars_files:
```

- **Terraform (declarative provisioning + lifecycle workflow)**: Terraform manages infrastructure using machine-readable configuration, emphasizing **repeatability** (same code across dev/stage/prod to avoid environment drift) and **audibility** (changes recorded as Git commits). Core workflow commands are **init** (initialize and download providers), **plan** (preview changes), **apply** (execute changes), and **destroy** (tear down). Terraform configurations are written in **HCL**, using blocks, arguments, and expressions; **input variables** parameterize configurations for reuse across environments.

- **Terraform OpenStack Provider (provider configuration + example)**: The OpenStack provider must be configured with valid credentials before managing resources. Example usage:

```hcl
terraform { required_version = ">= 0.14.0" required_providers { openstack = { source = "terraform-provider-openstack/openstack" version = "~> 1.53.0" } } } # Configure the OpenStack Provider provider "openstack" { user_name = "admin" tenant_name = "admin" password = "pwd" auth_url = "http://myauthurl:5000/v3" region = "RegionOne" } # Create a web server resource "openstack_compute_instance_v2" "test-server" { # ... }
```

For contributing/testing the provider, the docs recommend working against an OpenStack environment (often safer in a development cloud such as **DevStack**) and note that **acceptance tests** require specific OpenStack environment variables (e.g., image, flavor, floating IP pool).
