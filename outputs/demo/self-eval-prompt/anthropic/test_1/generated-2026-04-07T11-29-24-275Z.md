```hcl
# ══════════════════════════════════════════════════════════════
# MAIN TERRAFORM CONFIGURATION
#
# This file provisions a single web server on OpenStack with:
#   - A security group allowing SSH (22) and HTTP (80)
#   - A compute instance with a floating (public) IP
#   - An auto-generated Ansible inventory file
#
# LEARNING NOTE: Terraform files are declarative — you describe
# the *desired end state*, and Terraform figures out what API
# calls to make. If you run `terraform apply` twice with no
# changes, Terraform does nothing the second time.
# ══════════════════════════════════════════════════════════════

# ──────────────────────────────────────────────
# Terraform Settings & Provider Configuration
# ──────────────────────────────────────────────

terraform {
  # BEST PRACTICE: Pin both the minimum AND maximum Terraform
  # version to avoid surprises when the tool updates.
  required_version = ">= 1.3.0, < 2.0.0"

  required_providers {
    openstack = {
      source = "terraform-provider-openstack/openstack"
      # The "~>" constraint allows patch updates (1.53.x) but
      # blocks minor/major bumps that might break things.
      version = "~> 1.53.0"
    }
    local = {
      source  = "hashicorp/local"
      version = "~> 2.4"
    }
  }

  # CONCEPT: Terraform state stores the mapping between your
  # .tf code and real cloud resources. By default it's a local
  # file, but for teams you should use a remote backend (e.g.,
  # S3, Swift, Consul) so everyone shares the same state and
  # you get locking to prevent concurrent modifications.
  #
  # backend "s3" {
  #   bucket = "my-terraform-state"
  #   key    = "webserver/terraform.tfstate"
  #   region = "us-east-1"
  # }
}

# SECURITY BEST PRACTICE: We configure the OpenStack provider
# WITHOUT inline credentials. Terraform's OpenStack provider
# automatically reads the standard OpenStack environment
# variables (OS_AUTH_URL, OS_USERNAME, OS_PASSWORD, etc.) or
# a clouds.yaml file. This means:
#   1. Secrets never appear in .tf files
#   2. Secrets never end up in the Terraform state
#   3. Secrets never leak into CLI history
#
# To authenticate, either:
#   a) Source your OpenStack RC file:  source openrc.sh
#   b) Set env vars directly:         export OS_AUTH_URL=...
#   c) Use a clouds.yaml file
provider "openstack" {
  region = var.openstack_region
  # All other auth fields come from environment variables.
}

# ──────────────────────────────────────────────
# Local Values
# ──────────────────────────────────────────────

# CONCEPT: Locals are computed values you can reference
# throughout the configuration. They're great for
# consolidating tag maps and derived names.
locals {
  # Common tags applied to every resource for governance,
  # auditing, and cost tracking.
  common_tags = {
    "Environment" = var.environment
    "Owner"       = var.owner
    "ManagedBy"   = "terraform"
    "Application" = "web-server"
  }
}

# ──────────────────────────────────────────────
# Security Group
# ──────────────────────────────────────────────

# CONCEPT: A Security Group in OpenStack works like a firewall.
# By default, all inbound traffic is DENIED and all outbound
# traffic is ALLOWED. We explicitly open only the ports we need.
resource "openstack_networking_secgroup_v2" "web_sg" {
  name        = var.security_group_name
  description = "Security group for web server — allows SSH (22) and HTTP (80) inbound only"

  # NOTE: OpenStack security groups automatically include
  # default egress rules (allow all outbound). We only need
  # to add ingress rules below.
}

# RULE: Allow inbound SSH (port 22)
# SSH is needed for Ansible to connect and configure the server.
resource "openstack_networking_secgroup_rule_v2" "ssh_ingress" {
  direction         = "ingress"
  ethertype         = "IPv4"
  protocol          = "tcp"
  port_range_min    = 22
  port_range_max    = 22
  remote_ip_prefix  = var.allowed_ssh_cidr
  security_group_id = openstack_networking_secgroup_v2.web_sg.id
  description       = "Allow inbound SSH from ${var.allowed_ssh_cidr}"
}

# RULE: Allow inbound HTTP (port 80)
# This is the port Nginx will serve web traffic on.
resource "openstack_networking_secgroup_rule_v2" "http_ingress" {
  direction         = "ingress"
  ethertype         = "IPv4"
  protocol          = "tcp"
  port_range_min    = 80
  port_range_max    = 80
  remote_ip_prefix  = var.allowed_http_cidr
  security_group_id = openstack_networking_secgroup_v2.web_sg.id
  description       = "Allow inbound HTTP from ${var.allowed_http_cidr}"
}

# ──────────────────────────────────────────────
# Floating IP
# ──────────────────────────────────────────────

# CONCEPT: In OpenStack, instances get a *private* IP on the
# internal network. A "floating IP" is a public IP from an
# external pool that gets NATed to the private IP, making
# the instance reachable from outside.
resource "openstack_networking_floatingip_v2" "web_fip" {
  pool        = var.floating_ip_pool
  description = "Floating IP for ${var.instance_name}"
}

# ──────────────────────────────────────────────
# Compute Instance (the actual VM)
# ──────────────────────────────────────────────

resource "openstack_compute_instance_v2" "web_server" {
  name            = var.instance_name
  image_name      = var.image_name
  flavor_name     = var.flavor_name
  key_pair        = var.ssh_key_name
  security_groups = [openstack_networking_secgroup_v2.web_sg.name]

  # CONCEPT: `metadata` in OpenStack is a key-value store
  # attached to each instance. We use it for tagging —
  # the same way you'd use tags in AWS/Azure/GCP.
  metadata = local.common_tags

  network {
    name = var.network_name
  }

  # CONCEPT: `lifecycle` blocks control how Terraform manages
  # the resource over time.
  lifecycle {
    # If someone changes the image (e.g., from Ubuntu 22.04 to
    # 24.04), Terraform would normally destroy and recreate the
    # VM. `create_before_destroy` ensures the new VM is up
    # before the old one is removed, reducing downtime.
    create_before_destroy = true
  }
}

# ──────────────────────────────────────────────
# Associate Floating IP to Instance
# ──────────────────────────────────────────────

# This is a separate resource because the floating IP and the
# instance are independent objects in OpenStack's API. Splitting
# them means you can detach/reattach without destroying the VM.
resource "openstack_compute_floatingip_associate_v2" "web_fip_assoc" {
  floating_ip = openstack_networking_floatingip_v2.web_fip.address
  instance_id = openstack_compute_instance_v2.web_server.id
}

# ──────────────────────────────────────────────
# Generate Ansible Inventory File
# ──────────────────────────────────────────────

# CONCEPT: Instead of manually writing an Ansible inventory,
# we let Terraform generate it automatically using the IP it
# just allocated. This bridges the gap between provisioning
# (Terraform) and configuration (Ansible).
resource "local_file" "ansible_inventory" {
  content = templatefile("${path.module}/../ansible/inventory.ini.tpl", {
    web_server_ip    = openstack_networking_floatingip_v2.web_fip.address
    ssh_user         = var.ssh_user
    private_key_path = var.private_key_path
  })
  filename = "${path.module}/../ansible/inventory.ini"

  # SECURITY: Set restrictive file permissions (owner read/write
  # only) because the inventory contains the SSH key path and
  # the server IP — information an attacker could use.
  file_permission      = "0600"
  directory_permission = "0700"

  # Ensure the floating IP is actually associated before we
  # write the inventory, otherwise Ansible would try to connect
  # to an unreachable IP.
  depends_on = [openstack_compute_floatingip_associate_v2.web_fip_assoc]
}
```

```nginx
# ══════════════════════════════════════════════════════════════
# Nginx Server Block — auto-generated by Ansible.
# Manual edits will be overwritten on the next playbook run.
#
# CONCEPT: A "server block" in Nginx is equivalent to a
# "virtual host" in Apache. It defines how Nginx handles
# requests for a particular domain/port combination.
# ══════════════════════════════════════════════════════════════

server {
    # Listen on the configured port for both IPv4 and IPv6.
    # "default_server" means this block handles requests that
    # don't match any other server block.
    listen {{ nginx_listen_port }} default_server;
    listen [::]:{{ nginx_listen_port }} default_server;

    server_name {{ nginx_server_name }};

    # Document root — the directory Nginx serves files from.
    root {{ nginx_document_root }};
    index index.html;

    # SECURITY: Disable server version disclosure in HTTP
    # response headers. Attackers use version info to find
    # known vulnerabilities.
    server_tokens off;

    # SECURITY: Basic security headers to protect against
    # common web attacks.
    add_header X-Content-Type-Options "nosniff" always;
    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header X-XSS-Protection "1; mode=block" always;

    location / {
        # try_files checks for the requested file, then
        # directory, then returns a 404 if nothing matches.
        try_files $uri $uri/ =404;
    }

    # Logging — separate log files make debugging easier.
    access_log /var/log/nginx/webserver_access.log;
    error_log  /var/log/nginx/webserver_error.log;
}
```

### `ansible/playbook.yml`

```yaml
---
# ══════════════════════════════════════════════════════════════
# PLAYBOOK: Configure Nginx Web Server
#
# CONCEPT: A playbook is a YAML file that describes the desired
# state of your servers. Ansible reads it top-to-bottom,
# connects to each host via SSH, and applies the tasks.
#
# KEY PRINCIPLE: Idempotency — running this playbook multiple
# times produces the same result. If Nginx is already installed
# and configured correctly, Ansible reports "ok" and changes
# nothing. This makes it safe to re-run at any time.
# ══════════════════════════════════════════════════════════════

- name: Configure web server with Nginx
  hosts: webservers # Target all hosts in the [webservers] group
  become: true # Run tasks with sudo (root privileges)
  gather_facts: true # Collect system info (OS, IPs, etc.)

  # Load variables from the group_vars file. These control
  # the playbook's behavior without editing tasks.
  vars_files:
    - group_vars/all.yml

  # ── Pre-tasks run BEFORE the main task list ─────────────

  pre_tasks:
    - name: Display deployment information
      ansible.builtin.debug:
        msg:
          - '──────────────────────────────────────'
          - '  Nginx Web Server Configuration'
          - '──────────────────────────────────────'
          - '  Target host  : {{ inventory_hostname }}'
          - '  Listen port  : {{ nginx_listen_port }}'
          - '  Document root: {{ nginx_document_root }}'
          - '──────────────────────────────────────'

    # Cloud instances sometimes take a minute after booting
    # before the SSH daemon is ready. This task waits patiently
    # instead of failing immediately.
    - name: Wait for the instance to become reachable via SSH
      ansible.builtin.wait_for_connection:
        delay: 10 # Wait 10s before first attempt
        timeout: 300 # Give up after 5 minutes

    # Re-gather facts now that we have a stable connection.
    # This ensures variables like `ansible_os_family` are set.
    - name: Gather facts after connection is established
      ansible.builtin.setup:

  # ── Main tasks ──────────────────────────────────────────

  tasks:
    # ── Package Installation ──────────────────

    # CONCEPT: Ansible modules are cross-platform building
    # blocks. `apt` manages packages on Debian/Ubuntu;
    # `yum`/`dnf` manages them on RedHat/CentOS. We use
    # `when:` conditions so the right module runs on the
    # right OS family.

    - name: Update apt cache (Debian/Ubuntu)
      ansible.builtin.apt:
        update_cache: true
        cache_valid_time: 3600 # Skip if updated <1 hour ago
      when: ansible_os_family == "Debian"

    - name: Install Nginx (Debian/Ubuntu)
      ansible.builtin.apt:
        name: nginx
        state: present # Ensure installed, don't upgrade
      when: ansible_os_family == "Debian"

    - name: Install Nginx (RedHat/CentOS)
      ansible.builtin.yum:
        name: nginx
        state: present
      when: ansible_os_family == "RedHat"

    # ── Directory Setup ───────────────────────

    # Determine the correct web server user for the OS.
    # Debian uses "www-data", RedHat uses "nginx".
    # CONCEPT: `set_fact` creates a variable at runtime based
    # on conditions — this avoids hardcoding OS-specific values.
    - name: Set web server user based on OS family
      ansible.builtin.set_fact:
        web_user: "{{ 'www-data' if ansible_os_family == 'Debian' else 'nginx' }}"

    - name: Ensure document root directory exists
      ansible.builtin.file:
        path: '{{ nginx_document_root }}'
        state: directory
        owner: '{{ web_user }}'
        group: '{{ web_user }}'
        mode: '0755' # rwxr-xr-x

    # ── Deploy Static HTML ────────────────────
    # CONCEPT: The `template` module processes Jinja2 templates,
    # replacing {{ variables }} with actual values, then copies
    # the result to the remote host.
    - name: Deploy static index.html from template
      ansible.builtin.template:
        src: templates/index.html.j2
        dest: '{{ nginx_document_root }}/index.html'
        owner: '{{ web_user }}'
        group: '{{ web_user }}'
        mode: '0644' # rw-r--r--
      notify: Restart Nginx
      # CONCEPT: `notify` triggers a handler (defined below)
      # only if this task *actually changes* something. If the
      # file is already identical, Nginx won't be restarted.

    # ── Nginx Configuration ───────────────────

    - name: Remove default Nginx site configuration
      ansible.builtin.file:
        path: /etc/nginx/sites-enabled/default
        state: absent
      notify: Restart Nginx
      when: ansible_os_family == "Debian"

    - name: Deploy Nginx server block configuration
      ansible.builtin.template:
        src: templates/nginx.conf.j2
        dest: /etc/nginx/sites-available/webserver.conf
        owner: root
        group: root
        mode: '0644'
      notify: Restart Nginx
      when: ansible_os_family == "Debian"

    # CONCEPT: Nginx on Debian uses a sites-available /
    # sites-enabled pattern. Config files live in sites-available;
    # a symlink in sites-enabled "activates" them.
    - name: Enable Nginx server block (create symlink)
      ansible.builtin.file:
        src: /etc/nginx/sites-available/webserver.conf
        dest: /etc/nginx/sites-enabled/webserver.conf
        state: link
      notify: Restart Nginx
      when: ansible_os_family == "Debian"

    # BEST PRACTICE: Always validate the config before
    # restarting. A bad config would take Nginx down entirely.
    - name: Validate Nginx configuration syntax
      ansible.builtin.command: nginx -t
      changed_when: false # This is a read-only check
      register: nginx_test

    - name: Display Nginx config test result
      ansible.builtin.debug:
        msg: '{{ nginx_test.stderr_lines }}'

    # ── Service Management ────────────────────

    # CONCEPT: `systemd` module manages Linux services.
    # `enabled: true` = start on boot.
    # `state: started` = start now if not already running.
    - name: Enable and start Nginx service
      ansible.builtin.systemd:
        name: '{{ nginx_service_name }}'
        enabled: '{{ nginx_service_enabled }}'
        state: '{{ nginx_service_state }}'
        daemon_reload: true # Pick up any unit file changes

  # ── Handlers ────────────────────────────────────────────

  # CONCEPT: Handlers are like tasks, but they only run when
  # "notified" by another task. If multiple tasks notify the
  # same handler, it runs only ONCE at the end. This prevents
  # unnecessary service restarts.
  handlers:
    - name: Restart Nginx
      ansible.builtin.systemd:
        name: '{{ nginx_service_name }}'
        state: restarted

  # ── Post-tasks run AFTER the main task list ─────────────

  post_tasks:
    # Smoke test: verify the web server is actually responding.
    - name: Verify Nginx is responding on port {{ nginx_listen_port }}
      ansible.builtin.uri:
        url: 'http://localhost:{{ nginx_listen_port }}'
        status_code: 200
        return_content: false
      register: health_check
      retries: 3 # Try up to 3 times
      delay: 5 # Wait 5s between retries
      until: health_check.status == 200

    - name: Deployment summary
      ansible.builtin.debug:
        msg:
          - '══════════════════════════════════════'
          - '  ✅ Deployment Complete!'
          - '══════════════════════════════════════'
          - '  Nginx status : Running'
          - '  Health check : HTTP {{ health_check.status }}'
          - '  Access URL   : http://{{ ansible_host }}:{{ nginx_listen_port }}'
          - '══════════════════════════════════════'
```

### Prerequisites

| ------------- | --------------- | ---------------------------------------------------------- |

### Step 1 — Set Up Authentication (Secrets Stay Out of Files)

**Option A: Source your OpenStack RC file** (recommended):

```bash
# Download openrc.sh from your OpenStack dashboard:
# Project → API Access → Download OpenStack RC File
source openrc.sh
# You'll be prompted for your password — it stays in memory only.
```

**Option B: Export environment variables manually**:

```bash
export OS_AUTH_URL="https://your-openstack:5000/v3"
export OS_USERNAME="your-username"
export OS_PASSWORD="your-password"        # Consider using `read -s` to avoid shell history
export OS_PROJECT_NAME="your-project"
export OS_USER_DOMAIN_NAME="Default"
export OS_PROJECT_DOMAIN_NAME="Default"
export OS_REGION_NAME="RegionOne"
```

### Step 2 — Configure Terraform Variables

```bash
cd terraform/
cp terraform.tfvars.example terraform.tfvars
```

Edit `terraform.tfvars` — fill in only the **non-sensitive** values (instance name, network, SSH key name, etc.). Credentials are handled via environment variables from Step 1.

### Step 3 — Provision Infrastructure with Terraform

```bash
# Download provider plugins
terraform init

# Format your code (best practice before every commit)
terraform fmt

# Validate syntax and configuration
terraform validate

# Preview what will be created — review carefully!
terraform plan

# Apply — type 'yes' when prompted to create resources
terraform apply
```

After `apply` completes, note the outputs:

```
floating_ip = "192.168.1.100"

```

Terraform also generates `ansible/inventory.ini` automatically.

### Step 4 — Configure the Server with Ansible

```bash
cd ../ansible/

# Verify SSH connectivity first (always a good sanity check)
ansible -i inventory.ini webservers -m ping

# Run the playbook to install and configure Nginx
ansible-playbook -i inventory.ini playbook.yml
```

### Step 5 — Verify HTTP Access

**From a browser:**
Open the URL from the Terraform `web_url` output.

**From the command line:**

```bash
# Quick check
curl http://$(cd ../terraform && terraform output -raw floating_ip)

# Verbose check (shows headers, useful for debugging)
curl -v http://$(cd ../terraform && terraform output -raw floating_ip)
```

**Expected result:** An HTML page displaying **"Hello from OpenStack!"** with the server hostname and IP.

**Verify via SSH (for troubleshooting):**

```bash
# Get the SSH command (marked sensitive, requires -raw)
cd ../terraform
terraform output -raw ssh_command

# On the server:
sudo systemctl status nginx
curl -s localhost
sudo nginx -t
```

### Step 6 — Tear Down (When Finished)

```bash
cd ../terraform/
terraform destroy
# Type 'yes' to confirm. This removes ALL resources.
```

## Detailed Explanation of Improvements

### 1. Removed Inline Provider Credentials (🔴 Security — Critical)

**Before:** OpenStack credentials (`user_name`, `password`, `auth_url`) were defined as Terraform variables and passed directly to the provider block.

**After:** The provider block uses only the `region` parameter. All authentication is handled via OpenStack environment variables or `clouds.yaml`.

**Why:** When credentials are Terraform variables, they get stored in:

- The `terraform.tfvars` file (a file on disk)
- The Terraform **state file** in plaintext (even if marked `sensitive`)
- Potentially in shell history if passed via `-var` flags
- CI/CD logs if variable values are echoed

The OpenStack Terraform provider natively supports `OS_*` environment variables. Using this mechanism means credentials only exist in memory during the Terraform run and never touch the state file.

### 2. Added `.gitignore` (🟡 Security — Medium)

**Before:** No `.gitignore` was provided.

**After:** A comprehensive `.gitignore` prevents `terraform.tfvars`, state files, private keys, and generated inventories from being committed.

**Why:** This is a critical safety net. Even experienced developers accidentally `git add .` from time to time. The `.gitignore` ensures secrets and environment-specific files don't end up in the repository.

### 3. Added Input Validation Rules (🟢 Best Practice)

**Before:** Variables accepted any value.

**After:** Added `validation` blocks for `instance_name` (length check), `allowed_ssh_cidr`/`allowed_http_cidr` (valid CIDR check), and `environment` (enum check).

**Why:** Validation catches misconfigurations _before_ Terraform contacts the API, giving immediate feedback. A typo like `allowed_ssh_cidr = "10.0.0.0"` (missing `/prefix`) would cause a confusing API error from OpenStack. The validation block catches it with a clear message.

### 4. Added Resource Tagging via Metadata (🟡 Best Practice)

**Before:** No tags/metadata on resources.

**After:** Added `metadata` block with Environment, Owner, ManagedBy, and Application tags using a `locals` block.

**Why:** Tags are essential for:

- **Cost tracking:** "Which project is this VM charged to?"
- **Governance:** "Who owns this resource?"
- **Automation:** "Delete all resources tagged `environment=dev` nightly"
- **Auditing:** "Was this resource created by Terraform or manually?"

### 5. Restricted Generated Inventory File Permissions (🟡 Security)

**Before:** `local_file` used default permissions (typically `0644` — world-readable).

**After:** Set `file_permission = "0600"` and `directory_permission = "0700"`.

**Why:** The inventory file contains the SSH key path and server IP. On a shared machine (e.g., a CI runner), other users could read it. `0600` ensures only the file owner can read it.

### 6. Added Security Headers to Nginx (🟡 Security)

**Before:** Nginx served pages with default headers.

**After:** Added:

- `server_tokens off` — hides Nginx version from response headers
- `X-Content-Type-Options: nosniff` — prevents MIME-type sniffing
- `X-Frame-Options: SAMEORIGIN` — prevents clickjacking
- `X-XSS-Protection: 1; mode=block` — activates browser XSS filter

**Why:** These are low-cost, high-value security hardening measures. They don't affect functionality but significantly reduce the attack surface.

### 7. Fixed OS-Family-Dependent Web Server User (🟡 Portability)

**Before:** `www-data` was hardcoded as the owner of web files.

**After:** Added a `set_fact` task that sets `web_user` to `www-data` on Debian or `nginx` on RedHat.

**Why:** The playbook already had conditional package installation for Debian vs. RedHat, but the file ownership was always `www-data` — which doesn't exist on RedHat. This would cause the playbook to fail on CentOS/RHEL.

### 8. Marked Sensitive Outputs (🟡 Security)

**Before:** The `ssh_command` output (containing the private key path) was displayed in plaintext.

**After:** Added `sensitive = true` to the `ssh_command` output.

**Why:** Terraform outputs are often captured in CI/CD logs. Marking them sensitive ensures they're redacted in `terraform output` and log output. The operator can still retrieve the value with `terraform output -raw ssh_command` when needed.

### 9. Pinned Terraform Version Range (🟢 Best Practice)

**Before:** `required_version = ">= 0.14.0"` — allows any version including hypothetical Terraform 2.0 with breaking changes.

**After:** `required_version = ">= 1.3.0, < 2.0.0"`.

**Why:** An open-ended version constraint means someone running Terraform 2.0 (which might have breaking changes to HCL syntax or provider behavior) would proceed without warning. The upper bound ensures only compatible versions are used.

### 10. Added Extensive Pedagogical Comments (🟢 Learning)

**Before:** Minimal comments focused on section headers.

**After:** Every block includes explanatory comments that teach IaC concepts like:

- What declarative configuration means
- How Terraform state works
- What security groups are and how they work
- Why idempotency matters in Ansible
- What handlers are and why they exist
- How Jinja2 templates work

**Why:** The task explicitly targets junior developers new to DevOps. The comments transform the code from "just configuration" into a learning resource that explains the _why_ behind each decision.
