# Infrastructure as Code: Ansible and Terraform Summary

## Ansible Overview

Ansible is an **agentless IT automation tool** that connects to target systems primarily via SSH. It operates from a **control node** that pushes small modules to **managed nodes** without requiring agents, reducing overhead compared to agent-based alternatives.

### Key Characteristics
- Infrastructure is defined as desired state in **YAML playbooks**
- Modules are typically **idempotent** — rerunning playbooks converges systems to the same result, helping reduce configuration drift
- Supports **mutable infrastructure**, where changes are applied directly to existing systems
- Can automate full AWS web stacks (VPC, security groups, EC2, ALB) and deploy software like Nginx across environments
- Organizations can address drift through periodic playbook execution and monitoring to detect unexpected configuration changes

### Prerequisites for AWS Provisioning
- Python 3.8 or higher
- Ansible 2.14 or higher
- A UNIX-like control node with Python installed

### Example: Deploy Playbook (deploy.yml)
```yaml
---
- name: Deploy Web Application
  hosts: localhost
  connection: local
  gather_facts: false
  pre_tasks:
    - name: Display deployment information
      ansible.builtin.debug:
        msg:
          - " "
          - "Web Application Deployment Playbook"
          - " "
          - "This playbook will:"
          - " - Install Nginx on EC2 instances"
          - " - Deploy custom web application"
          - " - Configure and start services"
          - ""
          - "Note: Instances are in private subnets"
          - "Connection method: AWS Systems Manager (SSM)"
          - " "
    - name: Refresh dynamic inventory
      ansible.builtin.meta: refresh_inventory

- name: Configure web servers
  hosts: role_webserver
  gather_facts: true
  vars_files:
```

## Terraform Overview

Terraform is an IaC tool that manages and provisions infrastructure through machine-readable configuration files, replacing manual "ClickOps" processes. Its core value spans:

- **Repeatability**: Same configuration files across dev, staging, and production ensure identical infrastructure, eliminating environment drift by design
- **Audibility**: Every change is a Git commit, providing a permanent record of who changed what, when, and why

### Core Workflow
- **Init**: Initialize the working directory and download necessary providers
- **Plan**: Preview changes Terraform will make before execution
- **Apply**: Execute the plan to reach the desired state
- **Destroy**: Decommission managed infrastructure when no longer needed

### HCL (HashiCorp Configuration Language)
Terraform uses HCL, a domain-specific language with **blocks** (containers), **arguments** (key/value pairs), and **expressions** (computations). Input variables act as parameters that can be set externally (through files, environment variables, or at runtime) for reuse across environments.

### OpenStack Provider Example
```hcl
# Define required providers
terraform {
  required_version = ">= 0.14.0"
  required_providers {
    openstack = {
      source  = "terraform-provider-openstack/openstack"
      version = "~> 1.53.0"
    }
  }
}

# Configure the OpenStack Provider
provider "openstack" {
  user_name   = "admin"
  tenant_name = "admin"
  password    = "pwd"
  auth_url    = "http://myauthurl:5000/v3"
  region      = "RegionOne"
}

# Create a web server
resource "openstack_compute_instance_v2" "test-server" {
  # ...
}
```

The OpenStack provider's `auth_url` is required if `cloud` is not specified (or uses the `OS_AUTH_URL` environment variable). The `cloud` argument is required if `auth_url` is not specified.
