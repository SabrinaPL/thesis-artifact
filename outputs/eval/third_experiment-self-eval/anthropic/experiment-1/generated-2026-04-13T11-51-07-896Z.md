```hcl
# =============================================================
# main.tf — Core Infrastructure Resources
# =============================================================
# This is the "heart" of our Terraform configuration. It defines
# all the cloud resources we want to create:
#   1. Network infrastructure (virtual network, subnet, router)
#   2. Security groups (firewall rules)
#   3. Compute instances (virtual machines)
#   4. Floating IPs (public IP addresses)
#
# HOW TERRAFORM WORKS (for beginners):
#   - You write the DESIRED STATE of your infrastructure here.
#   - Terraform compares it to the CURRENT STATE (in the state file).
#   - It calculates a plan: what to create, update, or destroy.
#   - When you run 'terraform apply', it makes API calls to OpenStack
#     to make the real infrastructure match your desired state.
# =============================================================

# ---------------------------------------------------------------
# Provider Configuration
# ---------------------------------------------------------------
# The provider block tells Terraform HOW to communicate with
# OpenStack. Since we're using environment variables for auth
# (OS_AUTH_URL, OS_USERNAME, etc.), we don't need any config here.
# Terraform's OpenStack provider automatically reads OS_* env vars.

provider "openstack" {
  # Authentication is handled via environment variables.
  # See variables.tf for the list of required env vars.
  #
  # WHY environment variables instead of putting creds in this file?
  #   1. This file is committed to Git — secrets in Git are a major
  #      security incident (they persist in Git history forever).
  #   2. Env vars are per-session and never written to disk.
  #   3. Different team members can use their own credentials without
  #      modifying shared code.
}

# ---------------------------------------------------------------
# Data Sources
# ---------------------------------------------------------------
# "Data sources" fetch information about EXISTING resources that
# were NOT created by this Terraform config. Think of them as
# read-only lookups.

# Look up the external network (provided by your OpenStack admin).
# This network connects your project to the internet.
data "openstack_networking_network_v2" "external" {
  name = var.external_network_name
}

# Look up the OS image (e.g., Ubuntu 22.04) in the OpenStack image
# catalog. 'most_recent = true' picks the latest if multiple exist.
data "openstack_images_image_v2" "os_image" {
  name        = var.image_name
  most_recent = true
}

# Look up the compute flavor to determine VM sizing (CPU/RAM/disk).
data "openstack_compute_flavor_v2" "instance_flavor" {
  name = var.flavor_name
}

# ---------------------------------------------------------------
# Network Resources
# ---------------------------------------------------------------
# In cloud computing, you create "virtual networks" to isolate
# your VMs from other tenants. This is like having your own
# private network cable connecting only your machines.

# Create the virtual network (Layer 2 — think: the "cable")
resource "openstack_networking_network_v2" "internal" {
  name           = "${var.project_name}-internal-net"
  admin_state_up = true

  # BEST PRACTICE: Use variable-based naming so all resources
  # in this project share a consistent prefix.
}

# Create a subnet within the network (Layer 3 — think: "IP addresses")
# The subnet defines which IP addresses VMs on this network can use.
resource "openstack_networking_subnet_v2" "internal" {
  name            = "${var.project_name}-internal-subnet"
  network_id      = openstack_networking_network_v2.internal.id
  cidr            = var.internal_network_cidr
  ip_version      = 4
  dns_nameservers = var.dns_nameservers

  # dns_nameservers: Without these, VMs on this subnet can't resolve
  # domain names (e.g., apt can't find archive.ubuntu.com to install
  # packages). 8.8.8.8 is Google's public DNS.
}

# Create a router to connect our private network to the internet.
# Without a router, VMs can talk to each other but NOT to the outside.
resource "openstack_networking_router_v2" "router" {
  name                = "${var.project_name}-router"
  admin_state_up      = true
  external_network_id = data.openstack_networking_network_v2.external.id

  # external_network_id: Tells the router which network leads
  # to the internet, like setting a "default gateway."
}

# Attach our subnet to the router — this is the "cable" connecting
# our private network to the router.
resource "openstack_networking_router_interface_v2" "router_iface" {
  router_id = openstack_networking_router_v2.router.id
  subnet_id = openstack_networking_subnet_v2.internal.id
}

# ---------------------------------------------------------------
# Security Groups
# ---------------------------------------------------------------
# Security groups act as virtual firewalls. They define WHICH
# network traffic is allowed to reach your VMs and which is blocked.
#
# KEY CONCEPTS:
#   - "ingress" = incoming traffic (someone connecting TO your VM)
#   - "egress"  = outgoing traffic (your VM connecting TO somewhere)
#   - By default, all ingress is DENIED and all egress is ALLOWED.
#   - You add rules to explicitly ALLOW specific traffic.
#   - We set delete_default_rules = true to have full control over
#     what's allowed (no hidden default rules).

# ==================== Web Server Security Group ====================

resource "openstack_networking_secgroup_v2" "webserver_sg" {
  name        = "${var.project_name}-webserver-sg"
  description = "Firewall rules for web servers — allows SSH and internal HTTP only"

  # delete_default_rules removes OpenStack's auto-created egress rules.
  # We'll add our own explicitly so every rule is visible in code.
  # This follows the "principle of least privilege" — only allow
  # what you explicitly define.
  delete_default_rules = true
}

# Rule: Allow SSH (port 22) for remote management.
# NOTE: In production, replace var.allowed_ssh_cidr with your
# office/VPN IP range (e.g., "203.0.113.0/24") instead of 0.0.0.0/0.
resource "openstack_networking_secgroup_rule_v2" "ws_ssh_ingress" {
  direction         = "ingress"
  ethertype         = "IPv4"
  protocol          = "tcp"
  port_range_min    = 22
  port_range_max    = 22
  remote_ip_prefix  = var.allowed_ssh_cidr
  security_group_id = openstack_networking_secgroup_v2.webserver_sg.id
}

# Rule: Allow HTTP (port 80) ONLY from the internal network.
# This is a critical security control: web servers should only
# receive HTTP traffic from the load balancer (which is on the
# same internal network), NOT directly from the internet.
resource "openstack_networking_secgroup_rule_v2" "ws_http_ingress_internal" {
  direction         = "ingress"
  ethertype         = "IPv4"
  protocol          = "tcp"
  port_range_min    = var.webserver_port
  port_range_max    = var.webserver_port
  remote_ip_prefix  = var.internal_network_cidr  # <-- INTERNAL ONLY
  security_group_id = openstack_networking_secgroup_v2.webserver_sg.id
}

  security_group_id = openstack_networking_secgroup_v2.webserver_sg.id
}
```

### `ansible/generate_inventory.sh`

```bash
#!/usr/bin/env bash
# =============================================================
# generate_inventory.sh — Create Ansible inventory from Terraform
# =============================================================
# This script bridges Terraform and Ansible by reading Terraform's
# output values and generating an Ansible inventory file.
#
# WHY a script instead of a static inventory?
#   - IP addresses are assigned dynamically by OpenStack.
#   - We can't know them in advance.
#   - Terraform knows them after 'apply', so we extract them.
#
# USAGE: Run from the project root directory:
#   chmod +x ansible/generate_inventory.sh
#   ./ansible/generate_inventory.sh
# =============================================================

# 'set -euo pipefail' enables strict error handling:
#   -e: Exit immediately if any command fails
#   -u: Treat unset variables as errors
#   -o pipefail: A pipeline fails if ANY command in it fails
# This prevents the script from silently continuing after an error.
set -euo pipefail

TERRAFORM_DIR="./terraform"

# Verify Terraform directory exists and has state
if [ ! -d "$TERRAFORM_DIR" ]; then
    echo "ERROR: Terraform directory '$TERRAFORM_DIR' not found."
    echo "Run this script from the project root directory."
    exit 1
fi

echo "Reading Terraform outputs..."

# 'terraform output -raw' prints just the value (no quotes or newlines).
# We capture each output into a shell variable.
WS1_FIP=$(terraform -chdir="$TERRAFORM_DIR" output -raw webserver1_floating_ip)
WS2_FIP=$(terraform -chdir="$TERRAFORM_DIR" output -raw webserver2_floating_ip)
LB_FIP=$(terraform -chdir="$TERRAFORM_DIR" output -raw loadbalancer_floating_ip)

WS1_PRIV=$(terraform -chdir="$TERRAFORM_DIR" output -raw webserver1_private_ip)
WS2_PRIV=$(terraform -chdir="$TERRAFORM_DIR" output -raw webserver2_private_ip)

# Generate the inventory file using a "heredoc" (<<EOF ... EOF).
# This creates a multi-line string and writes it to a file.
cat > ansible/inventory.ini <<EOF
# =============================================================
# Ansible Inventory — AUTO-GENERATED by generate_inventory.sh
# Do not edit manually! Re-run the script after terraform apply.
# =============================================================

# Web servers group — these run nginx and serve HTML content.
# ansible_host: The IP Ansible uses to connect (floating/public IP).
# private_ip: The internal IP used by the load balancer to reach them.
# server_id: A unique identifier used in the HTML template.
[webservers]
webserver1 ansible_host=${WS1_FIP} private_ip=${WS1_PRIV} server_id=1
webserver2 ansible_host=${WS2_FIP} private_ip=${WS2_PRIV} server_id=2

# Load balancer group — runs nginx as a reverse proxy.
# webserver*_private_ip: Used in the upstream block configuration.
[loadbalancer]
loadbalancer ansible_host=${LB_FIP} webserver1_private_ip=${WS1_PRIV} webserver2_private_ip=${WS2_PRIV}
EOF

echo "✓ Inventory written to ansible/inventory.ini"
echo ""
echo "  Web Server 1:   ${WS1_FIP} (private: ${WS1_PRIV})"
echo "  Web Server 2:   ${WS2_FIP} (private: ${WS2_PRIV})"
echo "  Load Balancer:  ${LB_FIP}"
```

### `ansible/roles/webserver/tasks/main.yml`

```yaml
---
# =============================================================
# webserver/tasks/main.yml — Web Server Configuration Tasks
# =============================================================
# This file lists the tasks that configure each web server.
# Tasks run in order, top to bottom, on every host in the
# 'webservers' group.
#
# IDEMPOTENCY: Every task is designed to be "idempotent" — running
# it once or ten times produces the same result. This is a core
# principle of Ansible and IaC in general. You should be able to
# re-run this playbook safely without breaking anything.
# =============================================================

- name: Update apt package cache
  # 'apt' is the package manager on Debian/Ubuntu systems.
  # update_cache refreshes the list of available packages (like
  # running 'apt update' manually).
  # cache_valid_time: Skip the update if it was done less than
  # 3600 seconds (1 hour) ago — saves time on repeated runs.
  ansible.builtin.apt:
    update_cache: yes
    cache_valid_time: 3600

- name: Install nginx web server
  # 'state: present' means "ensure this package is installed."
  # If it's already installed, Ansible does nothing (idempotent).
  # Other options: 'latest' (upgrade to newest), 'absent' (remove).
  ansible.builtin.apt:
    name: nginx
    state: present

- name: Remove default nginx site configuration
  # Nginx ships with a default site that listens on port 80.
  # We remove it so it doesn't conflict with our custom config.
  # 'state: absent' means "ensure this file does NOT exist."
  ansible.builtin.file:
    path: /etc/nginx/sites-enabled/default
    state: absent
  notify: Reload nginx
  # 'notify' triggers the "Reload nginx" handler (defined in
  # handlers/main.yml) but ONLY if this task actually changed
  # something. If the file was already removed, the handler
  # is NOT triggered — another example of idempotency.

- name: Deploy nginx virtual host configuration
  # 'template' copies a Jinja2 template file to the target host,
  # substituting variables (like {{ webserver_port }}) with their
  # actual values. This is how we inject dynamic configuration.
  ansible.builtin.template:
    src: nginx-webserver.conf.j2
    dest: /etc/nginx/sites-available/webserver.conf
    owner: root
    group: root
    mode: "0644"       # Read/write for owner, read-only for others
  notify: Reload nginx

- name: Enable nginx virtual host (create symlink)
  # Nginx on Debian/Ubuntu uses a 'sites-available/sites-enabled'
  # pattern. Config files live in sites-available/, and you create
  # symlinks in sites-enabled/ to activate them.
  ansible.builtin.file:
    src: /etc/nginx/sites-available/webserver.conf
    dest: /etc/nginx/sites-enabled/webserver.conf
    state: link        # Create a symbolic link
  notify: Reload nginx

- name: Create web root directory
  # This is where our HTML files will live.
  # 'www-data' is the user that nginx runs as on Ubuntu.
  ansible.builtin.file:
    path: /var/www/html
    state: directory
    owner: www-data
    group: www-data
    mode: "0755"

- name: Deploy index.html identifying this server
  # Each web server gets a DIFFERENT index.html thanks to the
  # {{ inventory_hostname }} and {{ server_id }} variables in the
  # template. This lets us verify load balancing is working by
  # seeing which server responded.
  ansible.builtin.template:
    src: index.html.j2
    dest: /var/www/html/index.html
    owner: www-data
    group: www-data
    mode: "0644"

- name: Ensure nginx is running and enabled on boot
  # 'state: started' ensures nginx is running RIGHT NOW.
  # 'enabled: true' ensures nginx starts automatically after reboot.
  ansible.builtin.service:
    name: nginx
    state: started
    enabled: true
```

### `ansible/roles/webserver/templates/nginx-webserver.conf.j2`

```nginx
# =============================================================
# nginx-webserver.conf.j2 — Web Server Nginx Configuration
# =============================================================
# This is a Jinja2 template. Variables enclosed in {{ }} are
# replaced with actual values when Ansible deploys this file.
#
# On this server, {{ webserver_port }} will be replaced with the
# value from group_vars/all.yml (default: 80).
# =============================================================

server {
    # Listen on the configured port for both IPv4 and IPv6.
    # 'default_server' means this config handles requests that
    # don't match any other server block.
    listen {{ webserver_port }} default_server;
    listen [::]:{{ webserver_port }} default_server;

    # Document root — where nginx looks for files to serve.
    root /var/www/html;
    index index.html;

    # '_' is a catch-all server name — matches any hostname.
    server_name _;

    location / {
        # try_files attempts to serve the requested file.
        # $uri: Try the exact path requested.
        # $uri/: Try it as a directory (look for index.html inside).
        # =404: If neither works, return a 404 Not Found error.
        try_files $uri $uri/ =404;
    }
}
```

### `ansible/roles/loadbalancer/templates/nginx-lb.conf.j2`

```nginx
# =============================================================
# nginx-lb.conf.j2 — Load Balancer Nginx Configuration
# =============================================================
# This configures nginx as a reverse proxy with load balancing.
#
# TRAFFIC FLOW:
#   User (internet) ---> LB:{{ lb_port }} ---> upstream (Round-Robin)
#                                                ├── webserver1:{{ webserver_port }}
#                                                └── webserver2:{{ webserver_port }}
#
# LOAD BALANCING METHODS IN NGINX:
#   - round-robin (default): Requests go to each server in turn.
#   - least_conn: Sends to the server with fewest active connections.
#   - ip_hash: Same client IP always goes to same server (sticky).
#   - weighted: Servers with higher weights get more requests.
#
# We use the default Round-Robin — no special directive needed.
# =============================================================

# The 'upstream' block defines a group of backend servers.
# Nginx will distribute requests among them using Round-Robin
# (the default method — requests alternate: server1, server2, server1...).
upstream backend_webservers {
    # These are the PRIVATE (internal) IPs of the web servers.
    # The load balancer communicates with backends over the internal
    # network — this traffic never crosses the internet.
    server {{ webserver1_private_ip }}:{{ webserver_port }};
    server {{ webserver2_private_ip }}:{{ webserver_port }};
}

server {
    # Listen on the load balancer port (8082 by default).
    # NOTE: We intentionally do NOT listen on port 80.
    # This matches the security group which only allows {{ lb_port }}.
    listen {{ lb_port }} default_server;
    listen [::]:{{ lb_port }} default_server;

    server_name _;

    location / {
        # 'proxy_pass' tells nginx to forward the request to our
        # upstream group instead of serving local files.
        proxy_pass http://backend_webservers;

        # These headers preserve the original client's information
        # so the backend servers know who's really making the request.
        #
        # Without these, backends would see the load balancer's IP
        # as the client, losing the real user's identity.
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # Connection timeout settings — how long to wait for backends.
        # These prevent the LB from hanging if a backend is slow.
        proxy_connect_timeout 10s;
        proxy_read_timeout    30s;
        proxy_send_timeout    30s;
    }
}
```

## Detailed Explanation of Improvements

### 1. Credential Security (High Impact)

**Before:** OpenStack credentials were passed as Terraform variables with `sensitive = true`, encouraging users to put them in `terraform.tfvars`.

**After:** Removed credential variables entirely. The OpenStack provider reads standard `OS_*` environment variables automatically.

**Rationale:** Even with `sensitive = true`, Terraform stores variable values in the state file. Environment variables never touch disk. The `.tfvars.example` file originally included a placeholder for the password — a common antipattern that trains developers to put secrets in files.

### 2. `.gitignore` File (High Impact)

**Before:** No `.gitignore` existed. Anyone running `git add .` would commit `terraform.tfvars`, state files, and generated inventory containing credentials and infrastructure details.

**After:** Comprehensive `.gitignore` with comments explaining WHY each entry matters.

### 3. Security Group References by ID (Medium Impact)

**Before:** `security_groups = [openstack_networking_secgroup_v2.webserver_sg.name]` used the security group **name**.

**After:** Changed to reference by **ID**: `security_groups = [openstack_networking_secgroup_v2.webserver_sg.id]`

**Rationale:** Names can be ambiguous across projects in OpenStack. IDs are guaranteed unique. This prevents accidentally attaching the wrong security group if another project has a group with the same name.

### 4. SSH Access Restriction Variable (Medium Impact)

**Before:** SSH rules hardcoded `remote_ip_prefix = "0.0.0.0/0"` (open to entire internet).

**After:** Added `var.allowed_ssh_cidr` with a default of `0.0.0.0/0` but prominent comments urging restriction in production.

**Rationale:** SSH exposed to the internet is a prime target for brute-force attacks. Making it a variable with clear documentation nudges teams toward restricting it.

### 5. Resource Tagging (Low-Medium Impact)

**Before:** No metadata/tags on any resources.

**After:** Added `metadata` blocks on all instances with `environment`, `project`, and `role` tags, using variables for consistency.

**Rationale:** The best practices document specifically calls out "Consistent Resource Tagging" for governance, cost tracking, and audit. Metadata is OpenStack's equivalent of AWS tags.

### 6. Consistent Naming Convention (Low Impact)

**Before:** Resource names like `"lb-internal-net"` were hardcoded.

**After:** All names use `"${var.project_name}-*"` pattern (e.g., `"lb-webapp-internal-net"`).

**Rationale:** When you manage multiple projects in the same OpenStack tenant, consistent prefixing prevents name collisions and makes it easy to identify which resources belong to which project.

### 7. Ansible Configuration File (Low Impact)

**Before:** SSH settings scattered in `group_vars/all.yml`. No `ansible.cfg`.

**After:** Centralized `ansible.cfg` with SSH settings, pipelining, retry file configuration, and default inventory path.

**Rationale:** Reduces command-line arguments needed, enables SSH pipelining for performance, and provides a single place for Ansible behavior settings.

### 8. Version Constraints Separated (Low Impact)

**Before:** `terraform {}` block was in `main.tf`.

**After:** Moved to dedicated `versions.tf`.

**Rationale:** This is a widely-adopted Terraform convention. As `main.tf` grows with dozens of resources, having version constraints at the top gets lost. Separation keeps each file focused.

### 9. Proxy Timeouts Added (Low Impact)

**Before:** No timeout configuration in the nginx load balancer template.

**After:** Added `proxy_connect_timeout`, `proxy_read_timeout`, and `proxy_send_timeout`.

**Rationale:** Without timeouts, a hung backend could cause the load balancer to wait indefinitely, eventually exhausting connections and affecting all users.

### 10. Broken Handlers Fixed (Medium Impact)

**Before:** The original code had a garbled first attempt at `webserver/tasks/main.yml` with handlers defined inside the tasks block (invalid YAML), followed by a corrected version. This would confuse a junior developer following along.

**After:** Clean single version with handlers properly in `handlers/main.yml`.

### 11. Comprehensive Inline Comments (Pedagogical)

**Before:** Minimal comments, mostly describing WHAT the code does.

**After:** Extensive comments explaining WHY decisions were made, HOW concepts work, and teaching IaC fundamentals. Comments cover:
- What CIDR notation means
- Why idempotency matters
- How handlers differ from regular tasks
- What upstream blocks do in nginx
- The traffic flow through the system
- Why `try_files` works the way it does
- What `set -euo pipefail` does in bash
