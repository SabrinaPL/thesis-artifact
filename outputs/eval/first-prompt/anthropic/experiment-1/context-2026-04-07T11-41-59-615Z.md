# Infrastructure as Code (IaC) Summary

## Overview

Infrastructure as Code (IaC) is the practice of managing and provisioning computing infrastructure through machine-readable configuration files rather than manual processes. It delivers value through **repeatability** (same configuration across environments eliminates drift), **audibility** (every change tracked via Git commits), and consistent infrastructure management.

## Terraform

Terraform is an IaC tool that uses **HCL (HashiCorp Configuration Language)** — a domain-specific language with blocks, arguments, and expressions. The core workflow consists of four commands:

- **Init**: Initialize the working directory and download necessary providers
- **Plan**: Preview changes before execution
- **Apply**: Execute the plan to reach the desired state
- **Destroy**: Decommission managed infrastructure

Terraform supports **input variables** that act as parameters settable through files, environment variables, or at runtime, enabling code reuse across environments.

### OpenStack Provider Example

```
# Define required providers
terraform {
  required_version = ">= 0.14.0"
  required_providers {
    openstack = {
      source  = "terraform-provider-openstack/openstack"
      version = "~> 1.53.0"
    }
  }
}

# Configure the OpenStack Provider
provider "openstack" {
  user_name   = "admin"
  tenant_name = "admin"
  password    = "pwd"
  auth_url    = "http://myauthurl:5000/v3"
  region      = "RegionOne"
}

# Create a web server
resource "openstack_compute_instance_v2" "test-server" {
  # ...
}
```

The OpenStack provider can be configured via arguments (`auth_url`, `cloud`, `user_name`, `tenant_name`, etc.) or corresponding environment variables (e.g., `OS_AUTH_URL`).

## Ansible

Ansible is an **agentless** IT automation tool that connects to target systems primarily via SSH. It pushes small modules to managed nodes from a control node without requiring agent installation, reducing overhead. Ansible uses **YAML playbooks** to define desired state, and its modules are typically **idempotent** — rerunning playbooks converges systems to the same result.

Ansible supports **mutable infrastructure**, applying changes directly to existing systems. While flexible for rapid changes, this can accumulate configuration drift. Organizations mitigate drift through periodic playbook execution and monitoring.

### AWS Web Stack Example

Ansible can automate a complete AWS web stack (VPC, security groups, EC2, ALB) and deploy software like Nginx. Prerequisites for the control node include Python 3.8+ and Ansible 2.14+.

Example deployment playbook (`playbooks/deploy.yml`):

```
---
- name: Deploy Web Application
  hosts: localhost
  connection: local
  gather_facts: false
  pre_tasks:
    - name: Display deployment information
      ansible.builtin.debug:
        msg:
          - " "
          - "Web Application Deployment Playbook"
          - " "
          - "This playbook will:"
          - " - Install Nginx on EC2 instances"
          - " - Deploy custom web application"
          - " - Configure and start services"
          - ""
          - "Note: Instances are in private subnets"
          - "Connection method: AWS Systems Manager (SSM)"
          - " "
    - name: Refresh dynamic inventory
      ansible.builtin.meta: refresh_inventory

- name: Configure web servers
  hosts: role_webserver
  gather_facts: true
  vars_files:
```

This playbook demonstrates end-to-end infrastructure creation and application deployment using a single tool, installing Nginx on EC2 instances in private subnets via AWS Systems Manager (SSM) connectivity.
