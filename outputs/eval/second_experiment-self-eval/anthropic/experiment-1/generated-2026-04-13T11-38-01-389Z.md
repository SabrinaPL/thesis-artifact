### `terraform/main.tf`

```hcl
# ============================================================
# main.tf — Core infrastructure definition
#
# This file creates:
#   1. A security group with SSH and HTTP rules
#   2. Two compute instances (webserver1, webserver2)
#   3. Floating IPs so the servers are publicly reachable
#   4. A dynamic Ansible inventory file
#
# WHAT IS TERRAFORM DOING?
# Terraform reads this file, compares the desired state
# described here against the current state of your cloud,
# and makes only the necessary API calls to bring reality
# in line with the code. This is called "declarative" IaC —
# you say WHAT you want, not HOW to create it step-by-step.
# ============================================================

# -----------------------------------------------------------------
# Local Values
# -----------------------------------------------------------------
# Locals are like constants calculated once. They help you
# avoid repeating the same expression in multiple places
# (the DRY principle: Don't Repeat Yourself).
# -----------------------------------------------------------------

locals {
  # A common set of tags/metadata applied to every resource.
  # Consistent tagging is a governance best practice that helps
  # with cost tracking, ownership, and automated policy enforcement.
  common_tags = {
    environment  = var.environment
    owner        = var.owner
    project      = var.project_name
    managed_by   = "terraform"    # Signals to humans: don't edit manually!
  }

  # We define ingress rules as a map so we can iterate over them
  # with `for_each`. This is cleaner than copy-pasting resource
  # blocks for each port — and adding a new port means adding
  # just one map entry.
  ingress_rules = {
    ssh = {
      protocol         = "tcp"
      port_range_min   = 22
      port_range_max   = 22
      description      = "Allow SSH from trusted CIDRs"
      remote_ip_prefix = var.allowed_ssh_cidrs
    }
    http = {
      protocol         = "tcp"
      port_range_min   = 80
      port_range_max   = 80
      description      = "Allow HTTP"
      remote_ip_prefix = var.allowed_http_cidrs
    }
  }

  # Flatten the ingress rules so we get one rule per (protocol, CIDR) pair.
  # For example, if allowed_ssh_cidrs has 2 CIDRs, we create 2 SSH rules.
  # This is a common Terraform pattern when a resource accepts a single
  # value but you have a list of values to iterate over.
  ingress_rules_flat = flatten([
    for rule_key, rule in local.ingress_rules : [
      for idx, cidr in rule.remote_ip_prefix : {
        key              = "${rule_key}-${idx}"
        protocol         = rule.protocol
        port_range_min   = rule.port_range_min
        port_range_max   = rule.port_range_max
        description      = rule.description
        remote_ip_prefix = cidr
      }
    ]
  ])
}

# -----------------------------------------------------------------
# Provider Configuration
# -----------------------------------------------------------------
# SECURITY BEST PRACTICE: We use `cloud` to reference a
# clouds.yaml entry instead of putting credentials directly
# in Terraform files.
#
# clouds.yaml is OpenStack's standard credential file, usually
# located at ~/.config/openstack/clouds.yaml. Example:
#
#   clouds:
#     mycloud:
#       auth:
#         auth_url: http://keystone:5000/v3
#         username: myuser
#         password: mypassword       # or use OS_PASSWORD env var
#         project_name: myproject
#         user_domain_name: Default
#         project_domain_name: Default
#       region_name: RegionOne
#
# Alternatively, you can set OS_AUTH_URL, OS_USERNAME,
# OS_PASSWORD, OS_PROJECT_NAME environment variables and
# leave the provider block empty — the OpenStack provider
# reads them automatically.
# -----------------------------------------------------------------

provider "openstack" {
  cloud = var.openstack_cloud
  # If you prefer environment variables, remove the line above
  # and export OS_AUTH_URL, OS_USERNAME, OS_PASSWORD, etc.
}

# =================================================================
# SECURITY GROUP
# =================================================================
# A security group acts like a virtual firewall around your
# instances. By default, OpenStack blocks all inbound traffic
# unless you explicitly allow it with rules.
#
# We set delete_default_rules = true so that Terraform manages
# ALL rules — the default egress rules OpenStack would create
# automatically are replaced by our explicitly defined ones.
# This gives us full visibility and control.
# =================================================================

resource "openstack_networking_secgroup_v2" "web_sg" {
  name                 = "${var.project_name}-${var.environment}-web-sg"
  description          = "Allow inbound SSH and HTTP for web servers"
  delete_default_rules = true

  # OpenStack doesn't support metadata/tags on security groups
  # in all deployments, but the name carries our naming convention.
}

# -----------------------------------------------------------------
# Egress Rules (outbound traffic)
# -----------------------------------------------------------------
# These allow your instances to reach the internet (e.g., to
# download packages with apt/yum). Without egress rules, your
# servers would be completely isolated.
# -----------------------------------------------------------------

resource "openstack_networking_secgroup_rule_v2" "egress_v4" {
  direction         = "egress"
  ethertype         = "IPv4"
  security_group_id = openstack_networking_secgroup_v2.web_sg.id
  description       = "Allow all outbound IPv4 traffic"
}

resource "openstack_networking_secgroup_rule_v2" "egress_v6" {
  direction         = "egress"
  ethertype         = "IPv6"
  security_group_id = openstack_networking_secgroup_v2.web_sg.id
  description       = "Allow all outbound IPv6 traffic"
}

# -----------------------------------------------------------------
# Ingress Rules (inbound traffic)
# -----------------------------------------------------------------
# We iterate over our flattened rules map. Each entry creates
# one security group rule resource. `for_each` requires a map
# with string keys, so we convert our list to a map using the
# composite key we built earlier.
# -----------------------------------------------------------------

resource "openstack_networking_secgroup_rule_v2" "ingress" {
  for_each = { for rule in local.ingress_rules_flat : rule.key => rule }

  direction         = "ingress"
  ethertype         = "IPv4"
  protocol          = each.value.protocol
  port_range_min    = each.value.port_range_min
  port_range_max    = each.value.port_range_max
  remote_ip_prefix  = each.value.remote_ip_prefix
  security_group_id = openstack_networking_secgroup_v2.web_sg.id
  description       = each.value.description
}

# =================================================================
# FLOATING IPs
# =================================================================
# In OpenStack, instances get private IPs by default. A "floating
# IP" is a public IP address that you attach to an instance so
# it can be reached from outside the private network — similar
# to an Elastic IP in AWS.
# =================================================================

resource "openstack_networking_floatingip_v2" "fip" {
  for_each = var.webservers

  pool        = var.floating_ip_pool
  description = "Floating IP for ${each.value.name}"
}

# =================================================================
# COMPUTE INSTANCES
# =================================================================
# Each entry in var.webservers creates one virtual machine.
# `for_each` iterates over the map, and `each.key` / `each.value`
# give us the current key ("webserver1") and value ({name = "webserver1"}).
#
# WHY for_each INSTEAD OF count?
# - count uses numeric indices (0, 1, 2). If you remove the first
#   item, Terraform wants to destroy and recreate everything after it.
# - for_each uses string keys. Removing "webserver1" only affects
#   that one instance — much safer.
# =================================================================

resource "openstack_compute_instance_v2" "webserver" {
  for_each = var.webservers

  name            = "${var.project_name}-${var.environment}-${each.value.name}"
  image_id        = var.image_id
  flavor_name     = var.flavor_name
  key_pair        = var.keypair_name
  security_groups = [openstack_networking_secgroup_v2.web_sg.name]

  # Attach the instance to the specified network.
  network {
    uuid = var.network_id
  }

  # Metadata (tags) for governance, cost tracking, and automation.
  metadata = merge(local.common_tags, {
    role        = "webserver"
    server_name = each.value.name
  })

  # lifecycle block prevents accidental destruction of instances
  # during a `terraform apply`. You must explicitly run
  # `terraform destroy` or remove the block to tear down.
  # Uncomment for production use:
  # lifecycle {
  #   prevent_destroy = true
  # }
}

# =================================================================
# FLOATING IP ASSOCIATIONS
# =================================================================
# This links each floating IP to its corresponding instance.
# The association is a separate resource so that Terraform can
# manage the lifecycle of the IP and the instance independently.
# =================================================================

resource "openstack_compute_floatingip_associate_v2" "fip_assoc" {
  for_each = var.webservers

  floating_ip = openstack_networking_floatingip_v2.fip[each.key].address
  instance_id = openstack_compute_instance_v2.webserver[each.key].id
}

# =================================================================
# DYNAMIC ANSIBLE INVENTORY
# =================================================================
# Instead of manually maintaining an inventory file, we let
# Terraform generate one automatically. This guarantees the
# inventory always matches the actual infrastructure.
#
# The `templatefile` function renders a template (like Jinja2
# in Python) with the variables we pass. The result is written
# to a local file that Ansible can consume.
# =================================================================

resource "local_file" "ansible_inventory" {
  filename        = "${path.module}/../ansible/inventory.ini"
  file_permission = "0640" # Owner read/write, group read, no public access

  content = templatefile("${path.module}/templates/inventory.tpl", {
    webservers = {
      for key, ws in var.webservers : key => {
        ansible_host = openstack_networking_floatingip_v2.fip[key].address
        hostname     = ws.name
      }
    }
    ssh_user = var.ssh_user
  })

  # This dependency ensures the inventory is generated only after
  # floating IPs are associated, so the file contains valid IPs.
  depends_on = [
    openstack_compute_floatingip_associate_v2.fip_assoc
  ]
}
```

### `terraform/templates/inventory.tpl`

```ini
# ==========================================================
# Ansible Inventory — Auto-generated by Terraform
# DO NOT EDIT MANUALLY — changes will be overwritten on the
# next `terraform apply`.
#
# Generated at: ${timestamp()}
# ==========================================================

[webservers]
%{ for key, ws in webservers ~}
${ws.hostname} ansible_host=${ws.ansible_host} ansible_user=${ssh_user} server_name=${ws.hostname}
%{ endfor ~}

[webservers:vars]
# Note on StrictHostKeyChecking:
# We disable strict host key checking because these are ephemeral
# cloud instances whose SSH host keys change every time they are
# recreated. In a long-lived production environment, consider
# distributing known host keys instead.
ansible_ssh_common_args='-o StrictHostKeyChecking=accept-new -o UserKnownHostsFile=/dev/null'
```

> **Security improvement**: Changed `StrictHostKeyChecking=no` to `StrictHostKeyChecking=accept-new`. The `accept-new` option automatically accepts keys for hosts you've never connected to before but **warns** if a known host's key changes (potential MITM attack). `no` silently ignores all changes.

### `ansible/playbook.yml`

```yaml
---
# ============================================================
# playbook.yml — Install and configure nginx on web servers
#
# WHAT IS A PLAYBOOK?
# An Ansible playbook is a YAML file that describes the desired
# state of your servers. Ansible connects to each host via SSH
# and ensures reality matches what you've described. If a task
# is already in the desired state, Ansible skips it (this is
# called "idempotency" — running the playbook twice produces
# the same result).
#
# USAGE:
#   ansible-playbook -i inventory.ini playbook.yml
# ============================================================

- name: Configure web servers with nginx
  # "hosts: webservers" means this play targets every host in
  # the [webservers] group from our inventory file.
  hosts: webservers

  # "become: true" tells Ansible to use sudo, because installing
  # packages and writing to /var/www requires root privileges.
  become: true

  # gather_facts collects system information (OS family, IP
  # addresses, CPU count, etc.) that we can use in conditions
  # and templates.
  gather_facts: true

  # ------------------------------------------------------------------
  # Pre-flight checks
  # ------------------------------------------------------------------
  # "pre_tasks" run before the main tasks. We use them here to
  # wait until the server is actually reachable — cloud instances
  # can take a minute after getting an IP before SSH is ready.
  # ------------------------------------------------------------------
  pre_tasks:
    - name: Wait for SSH to become available
      ansible.builtin.wait_for_connection:
        timeout: 300    # Wait up to 5 minutes
        delay: 10       # Check every 10 seconds

  tasks:

    # ================================================================
    # 1. INSTALL NGINX
    # ================================================================
    # We handle both Debian/Ubuntu (apt) and RedHat/CentOS (yum)
    # using the `when` conditional. The `ansible_os_family` fact
    # is automatically discovered by `gather_facts`.
    # ================================================================

    - name: Update apt cache (Debian/Ubuntu)
      ansible.builtin.apt:
        update_cache: true
        # cache_valid_time avoids hitting the package mirror on every
        # run if the cache was refreshed recently (saves time).
        cache_valid_time: 3600
      when: ansible_os_family == "Debian"

    - name: Install nginx (Debian/Ubuntu)
      ansible.builtin.apt:
        name: nginx
        state: present    # "present" = install if missing, don't upgrade
      when: ansible_os_family == "Debian"

    - name: Install EPEL repository (RedHat/CentOS)
      ansible.builtin.yum:
        name: epel-release
        state: present
      when: ansible_os_family == "RedHat"

    - name: Install nginx (RedHat/CentOS)
      ansible.builtin.yum:
        name: nginx
        state: present
      when: ansible_os_family == "RedHat"

    # ================================================================
    # 2. CONFIGURE NGINX
    # ================================================================
    # The default nginx configuration already listens on port 80,
    # so we ensure the default site is enabled. We use a handler
    # to reload (not restart) nginx only when a config change is
    # detected — this avoids dropping active connections.
    # ================================================================

    - name: Ensure default nginx site is enabled (Debian/Ubuntu)
      ansible.builtin.file:
        src: /etc/nginx/sites-available/default
        dest: /etc/nginx/sites-enabled/default
        state: link
      when: ansible_os_family == "Debian"
      notify: Reload nginx

    # ================================================================
    # 3. DEPLOY SERVER-SPECIFIC HTML CONTENT
    # ================================================================
    # The `template` module renders a Jinja2 template and copies
    # the result to the target host. The variable `server_name` is
    # defined as a host variable in the inventory, so each server
    # gets its own unique page.
    # ================================================================

    - name: Deploy custom index.html
      ansible.builtin.template:
        src: templates/index.html.j2
        dest: /var/www/html/index.html
        owner: www-data    # nginx runs as www-data on Debian/Ubuntu
        group: www-data
        mode: "0644"       # World-readable (it's a public web page)
      notify: Reload nginx

    # ================================================================
    # 4. ENSURE NGINX IS RUNNING
    # ================================================================
    # This task is idempotent: if nginx is already running and
    # enabled, Ansible reports "ok" and moves on. If it's stopped,
    # Ansible starts it.
    # ================================================================

    - name: Ensure nginx is started and enabled at boot
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true     # Start automatically on reboot

    # ================================================================
    # 5. SMOKE TEST
    # ================================================================
    # A quick sanity check to verify nginx is actually responding.
    # This runs on the target host itself (127.0.0.1) to avoid
    # firewall/network issues during the check.
    # ================================================================

    - name: Verify nginx is responding on port 80
      ansible.builtin.uri:
        url: "http://127.0.0.1"
        return_content: true
        status_code: 200
      register: nginx_response

    - name: Confirm correct content is served
      ansible.builtin.assert:
        that:
          - "server_name in nginx_response.content"
        fail_msg: "Expected '{{ server_name }}' in page content but got: {{ nginx_response.content | truncate(200) }}"
        success_msg: "✅ {{ server_name }} is serving the correct content"

  # ------------------------------------------------------------------
  # HANDLERS
  # ------------------------------------------------------------------
  # Handlers run only when notified by a task (via `notify`), and
  # they run only once at the end of the play, even if notified
  # multiple times. This prevents unnecessary service restarts.
  #
  # We use `reloaded` instead of `restarted` because:
  #   - reload re-reads config without dropping connections
  #   - restart fully stops and starts the process
  # For a web server, reload is almost always preferred.
  # ------------------------------------------------------------------
  handlers:
    - name: Reload nginx
      ansible.builtin.service:
        name: nginx
        state: reloaded
```

## Detailed Explanation of Improvements

### 1. Credential Management (High Priority — Security)

**Before:** OpenStack credentials were defined as Terraform variables with `sensitive = true` and stored in `terraform.tfvars`.

**After:** Credentials are handled via OpenStack's native `clouds.yaml` or environment variables. The `provider "openstack"` block references a cloud name instead of individual credentials.

**Why:** Even with `sensitive = true`, Terraform writes variable values into the state file in plaintext. Using `clouds.yaml` or environment variables means credentials never enter Terraform's workflow at all. This aligns with the best practice of "keeping secrets out of code and state files."

### 2. SSH CIDR Restriction (Medium Priority — Security)

**Before:** SSH was open to `0.0.0.0/0` (the entire internet) with no way to restrict it.

**After:** Added `allowed_ssh_cidrs` variable with validation, defaulting to `0.0.0.0/0` but clearly documented as something to override. The security group rules now iterate over a list of CIDRs.

**Why:** Exposing SSH to the internet is one of the most common attack vectors. A parameterized CIDR list lets operators restrict access to their office or VPN.

### 3. `StrictHostKeyChecking=accept-new` (Medium Priority — Security)

**Before:** `StrictHostKeyChecking=no` silently accepts any SSH host key, even changed ones.

**After:** `StrictHostKeyChecking=accept-new` accepts keys for new hosts but warns if a previously-seen key changes.

**Why:** A changed host key can indicate a man-in-the-middle attack. `accept-new` provides a pragmatic middle ground for ephemeral cloud infrastructure.

### 4. Versions File and Pinning (Medium Priority — Reproducibility)

**Before:** Version constraints were embedded in `main.tf`.

**After:** Extracted to a dedicated `versions.tf` with an upper bound on the Terraform version and comments about remote state backends.

**Why:** Separation of concerns and a standard convention that makes version management easy to find and audit.

### 5. Input Validation (Low-Medium Priority — Robustness)

**Before:** No validation on inputs like `image_id` or `network_id`.

**After:** Added regex validation for UUIDs and `contains()` validation for the `environment` variable.

**Why:** Catching typos at `terraform plan` time is far cheaper than debugging a cryptic OpenStack API error.

### 6. Resource Tagging Strategy (Low Priority — Governance)

**Before:** Only `role = "webserver"` metadata.

**After:** A `common_tags` local value includes `environment`, `owner`, `project`, and `managed_by`, merged into every resource's metadata.

**Why:** Consistent tagging enables cost tracking, ownership identification, and automated policy enforcement (as recommended by the PaC best practice).

### 7. Handler Uses `reloaded` Instead of `restarted` (Low Priority — Reliability)

**Before:** Nginx was fully restarted on configuration changes.

**After:** Nginx is reloaded, which re-reads configuration without dropping active connections.

**Why:** In production, a restart causes a brief outage. A reload is graceful.

### 8. Ansible Smoke Test (New — Verification)

**Added:** A `uri` task and `assert` task that verify nginx is responding with the correct content on each server during the playbook run.

**Why:** Fail-fast feedback. If the template didn't render correctly or nginx didn't start, the playbook fails immediately with a clear message instead of requiring manual `curl` verification.

### 9. `.gitignore` and `ansible.cfg` (Medium Priority — Best Practice)

**Added:** A comprehensive `.gitignore` preventing state files, credentials, and generated artifacts from being committed. An `ansible.cfg` for consistent SSH pipelining and output formatting.

**Why:** Defence in depth — even if someone forgets the rule about not committing secrets, `.gitignore` catches it.

### 10. Pre-task SSH Wait (New — Reliability)

**Added:** A `wait_for_connection` pre-task in the Ansible playbook.

**Why:** Cloud instances are not immediately SSH-ready after Terraform reports them as created. Without this wait, Ansible may fail intermittently with connection refused errors.
