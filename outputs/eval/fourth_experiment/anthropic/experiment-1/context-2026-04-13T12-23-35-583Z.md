# Summary: Infrastructure as Code (IaC) Best Practices with Terraform and Ansible

## Core Value Proposition of IaC

Infrastructure as Code (IaC) tools like Terraform enable managing and provisioning infrastructure through machine-readable configuration files rather than manual processes. This approach delivers value across key dimensions:

- **Repeatability**: Using the same configuration files across development, staging, and production ensures identical infrastructure, eliminating environment drift by design.
- **Audibility**: Every change is a Git commit, providing a permanent record of who changed what, when, and why.

## Terraform Best Practices

1. **Use version control and prevent manual changes**: Treat infrastructure configurations as application code. Embrace a GitOps approach and implement automated CI/CD workflows to apply changes.

2. **Shift culture to collaborative IaC**: Enable usage across teams with self-service infrastructure, apply policies and compliance according to organizational standards, and leverage relevant insights.

3. **Code quality tooling**: Run `terraform fmt` and `terraform validate` as part of CI pipelines, and require human approval on plans before applying changes.

4. **Provisioners as a last resort**: Terraform is primarily designed for immutable infrastructure. For post-apply operations (uploading files, running commands/scripts), use purpose-built solutions first. Only use Terraform provisioners when no provider-native mechanism exists.

## Ansible for IaC

Ansible supports **mutable infrastructure**, where changes are applied directly to existing systems. This offers flexibility for rapid changes but can accumulate configuration drift over time. Organizations can address drift through periodic playbook execution and monitoring.

Ansible can provision cloud infrastructure on AWS (VPC networking, security groups, EC2 instances, Application Load Balancers) and deploy applications like Nginx web servers. After deployment, resources should be cleaned up to avoid charges:

```
ansible-playbook playbooks/teardown yml
```

## NGINX Load Balancing

NGINX can serve as an HTTP load balancer across multiple application instances to optimize resource utilization, maximize throughput, reduce latency, and ensure fault tolerance. Server groups are defined using the `upstream` directive:

```nginx
http {
    upstream backend {
        server backend1.example.com weight=5;
        server backend2.example.com;
        server 192.0.0.1 backup;
    }
}
```

## Tooling Integration

Platforms like Spacelift can manage multiple infrastructure tools (Ansible, Terraform, OpenTofu, Pulumi, AWS CloudFormation, Kubernetes) from a single place, combining stacks and building workflows across tools with GitOps flows, custom workflows based on pull requests, and compliance checks.
