### `ansible/playbooks/nfs_server.yml`

```yaml
---
# ──────────────────────────────────────────────
# Playbook: Configure NFS Server
# ──────────────────────────────────────────────
- name: Configure NFS Server
  hosts: nfs
  become: true
  vars:
    nfs_export_path: "{{ nfs_export_path | default('/srv/nfs/webdata') }}"
    nfs_device: "{{ nfs_device | default('/dev/xvdf') }}"
    nfs_filesystem_type: "{{ nfs_filesystem_type | default('ext4') }}"
    web_server_ips: '{{ web_server_ips }}'
    web_content: "{{ web_content | default('<h1>Hello from NFS</h1>') }}"

  tasks:
    # ── Package Installation ──
    - name: Update apt cache
      apt:
        update_cache: true
        cache_valid_time: 3600

    - name: Install NFS server packages
      apt:
        name:
          - nfs-kernel-server
          - nfs-common
        state: present

    # ── Volume Preparation ──
    - name: Check if the EBS volume has a filesystem
      command: blkid {{ nfs_device }}
      register: blkid_result
      failed_when: false
      changed_when: false

    - name: Create filesystem on attached volume
      filesystem:
        fstype: '{{ nfs_filesystem_type }}'
        dev: '{{ nfs_device }}'
      when: blkid_result.rc != 0

    - name: Create NFS export directory
      file:
        path: '{{ nfs_export_path }}'
        state: directory
        owner: nobody
        group: nogroup
        mode: '0755'

    - name: Mount the attached volume
      mount:
        path: '{{ nfs_export_path }}'
        src: '{{ nfs_device }}'
        fstype: '{{ nfs_filesystem_type }}'
        opts: defaults
        state: mounted

    - name: Set permissions on mounted directory
      file:
        path: '{{ nfs_export_path }}'
        owner: nobody
        group: nogroup
        mode: '0755'

    # ── Seed Default Web Content ──
    - name: Create default index.html on NFS share
      copy:
        dest: '{{ nfs_export_path }}/index.html'
        content: '{{ web_content }}'
        owner: nobody
        group: nogroup
        mode: '0644'
        force: false # Don't overwrite if content already exists

    # ── NFS Exports ──
    - name: Configure NFS exports
      template:
        src: ../templates/exports.j2
        dest: /etc/exports
        owner: root
        group: root
        mode: '0644'
      notify: Restart NFS server

    - name: Export all NFS shares
      command: exportfs -ra
      changed_when: false

    # ── Service Management ──
    - name: Enable and start NFS server
      systemd:
        name: nfs-kernel-server
        state: started
        enabled: true

  handlers:
    - name: Restart NFS server
      systemd:
        name: nfs-kernel-server
        state: restarted
```

## 5. Explanations

### Storage Architecture (Volume + NFS)

The storage architecture implements a two-tier shared storage pattern:

1. **Block Storage Layer (EBS Volume)**: Terraform provisions an encrypted EBS volume (`aws_ebs_volume`) as durable, persistent block storage. This volume survives instance termination and can be snapshotted for backups. It is attached to the NFS server instance via `aws_volume_attachment` at the device path `/dev/xvdf`.

2. **Network File System Layer (NFS)**: Ansible configures the NFS server to:
   - Format the raw block device with ext4 (idempotently — only if no filesystem exists)
   - Mount it at `/srv/nfs/webdata`
   - Export this directory via NFS to only the web server IPs (least-privilege access)

3. **Web Server Consumption**: Both web servers mount the NFS export at `/var/www/shared` using the `_netdev` mount option (ensuring the network is available before mount). NGINX serves content directly from this mount point.

**Benefits of this architecture:**

- **Single source of truth**: Content updated once on the NFS share is immediately available to all web servers — no synchronization or deployment to multiple nodes required
- **Persistence**: The EBS volume persists independently of the NFS instance lifecycle. If the NFS server is rebuilt, the volume can be reattached with all data intact
- **Consistency**: Both web servers serve identical content at all times, eliminating the class of bugs caused by inconsistent deployments across nodes

### CI/CD Workflow

The GitLab CI pipeline implements a **four-stage progressive deployment**:

```
validate → plan → apply (manual gate) → configure (manual gate)
```

1. **Validate Stage** (`terraform:init`):
   - Initializes Terraform with the remote backend configuration
   - Runs `terraform fmt -check` to enforce consistent formatting
   - Runs `terraform validate` to catch syntax/logic errors
   - Triggers on both merge requests and default branch commits, providing early feedback

2. **Plan Stage** (`terraform:plan`):
   - Generates an execution plan saved as `tfplan` artifact
   - The plan shows exactly what will change — reviewers can inspect it in MR discussions
   - Uses `-input=false` to prevent interactive prompts in CI

3. **Apply Stage** (`terraform:apply`):
   - **Manual gate** (`when: manual`): Requires a human to click "Run" after reviewing the plan — this is a critical safety measure for infrastructure changes
   - Applies the saved plan file (not re-planning, which could produce different results)
   - Exports Terraform outputs as JSON for the Ansible stage
   - Only runs on the default branch (not on merge requests)

4. **Configure Stage** (`ansible:configure`):
   - Parses Terraform outputs to dynamically generate the Ansible inventory
   - Writes the SSH private key (from masked CI/CD variable) securely
   - Configures SSH ProxyCommand to reach private-subnet instances through the load balancer
   - Runs the master playbook (`site.yml`) which orchestrates NFS → Web → LB in order

**Security measures throughout:**

- `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `SSH_PRIVATE_KEY`, and `KEY_PAIR_NAME` are stored as **masked CI/CD variables** in GitLab — never in the repository
- `terraform.tfvars` is gitignored; all values come from environment variables (`TF_VAR_*` prefix)
- Plan artifacts expire after 1 hour to limit exposure

### Terraform State Management Approach

The solution uses an **S3 remote backend with DynamoDB state locking**:

```
┌─────────────────┐     ┌──────────────────────┐
│  GitLab Runner   │────▶│  S3 Bucket (encrypted)│  ← State file
│  (terraform)     │     └──────────────────────┘
│                  │     ┌──────────────────────┐
│                  │────▶│  DynamoDB Table       │  ← Lock record
└─────────────────┘     └──────────────────────┘
```

**Why remote state?**

- **Collaboration**: Multiple team members and CI runners can access the same state. Local state would create conflicts.
- **Locking**: The DynamoDB table prevents concurrent `terraform apply` operations — if two pipelines run simultaneously, the second will wait or fail rather than corrupting state.
- **Encryption at rest**: The `encrypt = true` flag ensures the state file (which contains sensitive values like IPs and resource IDs) is encrypted in S3.
- **Versioning**: S3 bucket versioning (configured outside this project) enables rollback if state becomes corrupted.

**Backend configuration is injected at runtime** via `-backend-config` flags rather than hardcoded in `backend.tf`. This ensures:

- The same Terraform code works across environments (dev/staging/production) by varying only the state key
- Bucket names and credentials are never committed to source control
- The state key includes the environment name (`infra/${CI_ENVIRONMENT_NAME}/terraform.tfstate`), enabling environment isolation within a single bucket

**State is the single source of truth** for what Terraform manages. The `terraform plan` stage compares desired configuration against current state to show exactly what will change, enabling the manual approval gate to be meaningful — reviewers know precisely what they are approving.
