### `ansible/playbooks/nfs_server.yml`

```yaml
---
# Playbook: Configure NFS Server
# - Formats and mounts the attached block storage volume
# - Installs NFS server packages
# - Exports a shared directory to web servers

- name: Configure NFS Server
  hosts: nfs_servers
  become: true

  vars:
    nfs_mount_point: /srv/nfs/shared
    nfs_volume_device: "{{ hostvars[inventory_hostname]['nfs_volume_device'] | default('/dev/vdb') }}"
    nfs_filesystem_type: ext4
    nfs_export_network: "{{ lookup('env', 'NETWORK_CIDR') | default('10.0.1.0/24', true) }}"
    nfs_export_options: 'rw,sync,no_subtree_check,no_root_squash'

  tasks:
    - name: Install NFS server packages
      apt:
        name:
          - nfs-kernel-server
          - nfs-common
        state: present
        update_cache: true

    - name: Create filesystem on the attached volume
      filesystem:
        fstype: '{{ nfs_filesystem_type }}'
        dev: '{{ nfs_volume_device }}'

    - name: Create the NFS mount point directory
      file:
        path: '{{ nfs_mount_point }}'
        state: directory
        owner: nobody
        group: nogroup
        mode: '0755'

    - name: Mount the block storage volume
      mount:
        path: '{{ nfs_mount_point }}'
        src: '{{ nfs_volume_device }}'
        fstype: '{{ nfs_filesystem_type }}'
        opts: defaults
        state: mounted

    - name: Set permissions on mounted directory
      file:
        path: '{{ nfs_mount_point }}'
        owner: nobody
        group: nogroup
        mode: '0755'

    - name: Create default index page for web content
      copy:
        dest: '{{ nfs_mount_point }}/index.html'
        content: |
          <!DOCTYPE html>
          <html>
          <head><title>Shared NFS Web Content</title></head>
          <body>
            <h1>Hello from NFS-backed web application!</h1>
            <p>Served from shared persistent storage.</p>
          </body>
          </html>
        owner: nobody
        group: nogroup
        mode: '0644'
        force: false # Do not overwrite if content already exists

    - name: Configure NFS exports
      template:
        src: ../templates/exports.j2
        dest: /etc/exports
        owner: root
        group: root
        mode: '0644'
      notify: Restart NFS server

    - name: Ensure NFS server is running and enabled
      systemd:
        name: nfs-kernel-server
        state: started
        enabled: true

  handlers:
    - name: Restart NFS server
      systemd:
        name: nfs-kernel-server
        state: restarted
```

---
# Playbook: Configure Web Servers
# - Installs nginx
# - Mounts NFS shared directory
# - Configures nginx to serve content from the NFS mount

- name: Configure Web Servers
  hosts: web_servers
  become: true

  vars:
    nfs_server_ip: "{{ lookup('env', 'NFS_SERVER_IP') }}"
    nfs_remote_path: /srv/nfs/shared
    nfs_local_mount: /var/www/shared
    nginx_document_root: /var/www/shared

  tasks:
    - name: Install required packages
      apt:
        name:
          - nginx
          - nfs-common
        state: present
        update_cache: true

    - name: Create local NFS mount point
      file:
        path: '{{ nfs_local_mount }}'
        state: directory
        owner: www-data
        group: www-data
        mode: '0755'

    - name: Mount NFS shared directory
      mount:
        path: '{{ nfs_local_mount }}'
        src: '{{ nfs_server_ip }}:{{ nfs_remote_path }}'
        fstype: nfs
        opts: defaults,_netdev,soft,timeo=15
        state: mounted

    - name: Deploy nginx virtual host configuration
      template:
        src: ../templates/nginx_web.conf.j2
        dest: /etc/nginx/sites-available/default
        owner: root
        group: root
        mode: '0644'

      systemd:
        name: nginx
        state: started
        enabled: true

### Storage Architecture (Volume + NFS)

```
┌─────────────────────────────────────────────────────────────┐
│                     External Network                        │
│                          │                                  │
│                   ┌──────┴───────┐                          │

│              └─────┬───────┬─────────┘                      │

│              └────────┬───────────┘                         │

│              ┌────────┴───────────┐                         │
│              │    NFS Server      │                         │
│              │  /srv/nfs/shared   │                         │
│              └────────┬───────────┘                         │
│                       │                                     │
│              ┌────────┴───────────┐                         │
│              │  Block Storage     │                         │
│              │  Volume (50 GB)    │                         │
│              └────────────────────┘                         │
│                                                             │
│                Internal Network (10.0.1.0/24)               │
└─────────────────────────────────────────────────────────────┘
```

The storage architecture uses a **two-layer approach** that separates persistent storage from compute:

1. **Block Storage Volume**: Terraform provisions a dedicated block storage volume (configurable size, default 50 GB) and attaches it to the NFS server instance. This volume persists independently of the compute instance — if the NFS server VM is destroyed and recreated, the data on the volume survives as long as the volume resource itself is not destroyed. This is the foundation of data durability.

2. **NFS Layer**: The Ansible NFS playbook formats the attached volume (ext4), mounts it to `/srv/nfs/shared`, and configures `nfs-kernel-server` to export this directory. The export is restricted to the internal subnet CIDR, ensuring only web servers within the private network can mount the share.

3. **Web Server Mounts**: Each web server mounts the NFS export at `/var/www/shared` using the `_netdev` option (ensuring the mount waits for network availability) and `soft,timeo=15` options (preventing hard-locks if NFS becomes temporarily unavailable). Nginx serves content directly from this mounted directory.

**Key benefit**: Content updates need only be made once on the NFS share. Both web servers immediately serve the updated content without any deployment step, replication mechanism, or synchronization tooling.

### CI/CD Workflow

The GitLab CI pipeline implements a **four-stage progression** with a manual approval gate:

```
validate → plan → apply (manual gate) → configure
```

1. **Validate Stage** (`terraform_init`):
   - Runs `terraform init` to initialize the working directory and download provider plugins.
   - Runs `terraform validate` to check configuration syntax and internal consistency.
   - Runs `terraform fmt -check` to enforce consistent formatting as a code quality gate.
   - Artifacts (`.terraform` directory) are passed to subsequent stages.

2. **Plan Stage** (`terraform_plan`):
   - Runs `terraform plan` and saves the execution plan to a file (`tfplan`).
   - The plan artifact captures the exact set of changes that will be applied, ensuring no drift between plan review and apply.

3. **Apply Stage** (`terraform_apply`):
   - **Manual trigger required** — a team member must review the plan output and click "Play" in the GitLab UI. This provides human oversight before any infrastructure is modified, aligning with the IaC best practice of "CI plans with human approval before applying."
   - Runs `terraform apply` using the saved plan file for deterministic execution.
   - Exports Terraform outputs to JSON for the Ansible stage.
   - Restricted to the `main` branch only, preventing accidental infrastructure changes from feature branches.

4. **Configure Stage** (`ansible_configure`):
   - Parses Terraform outputs to discover instance IPs and volume device paths.
   - Runs playbooks in dependency order: NFS server first (must be ready before web servers can mount), then web servers, then load balancer.
   - SSH key is injected from a protected CI/CD variable — never stored in the repository.

### Terraform State Management Approach

State management follows the principle that **state is a critical shared resource** that must be stored remotely, encrypted, and protected from concurrent modification:

1. **Remote Backend (S3-compatible)**: The `backend "s3"` configuration stores state in an S3 bucket (or any S3-compatible service like MinIO). This ensures:
   - **Persistence**: State survives beyond any single CI runner's lifecycle.
   - **Shareability**: Multiple team members and CI pipelines access the same state.
   - **Encryption at rest**: The `encrypt = true` flag ensures the state file, which may contain sensitive values, is encrypted server-side.

2. **State Locking** (`dynamodb_table`): A DynamoDB table provides distributed locking. When `terraform apply` runs, it acquires a lock in DynamoDB, preventing concurrent operations from corrupting state. This is critical in CI/CD where multiple pipelines could theoretically run simultaneously.

3. **Credential Isolation**: Backend credentials (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`) are stored exclusively as GitLab CI/CD **masked and protected** variables. They are:
   - Masked in job logs (GitLab redacts them from output).
   - Protected (only available on protected branches like `main`).
   - Never committed to version control.

4. **State as Single Source of Truth**: By storing state remotely and requiring all changes to flow through the CI/CD pipeline, manual `terraform apply` commands from developer machines are discouraged. The pipeline enforces that all infrastructure changes are auditable Git commits — every change to infrastructure is traceable to a merge request, a reviewer, and a pipeline execution.
