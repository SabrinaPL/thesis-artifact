## `ansible/nfs.yml`

```yaml
---
- name: Configure NFS server
  hosts: nfs
  become: true
  tasks:
    - name: Install NFS packages
      apt:
        name:
          - nfs-kernel-server
        state: present
        update_cache: true

    - name: Create filesystem on attached volume
      filesystem:
        fstype: "{{ nfs_filesystem_type }}"
        dev: "{{ nfs_mount_device }}"

    - name: Create mount point
      file:
        path: "{{ nfs_mount_point }}"
        state: directory
        mode: "0755"

    - name: Mount attached volume
      mount:
        path: "{{ nfs_mount_point }}"
        src: "{{ nfs_mount_device }}"
        fstype: "{{ nfs_filesystem_type }}"
        opts: defaults
        state: mounted

    - name: Create shared export directory
      file:
        path: "{{ nfs_export_path }}"
        state: directory
        mode: "0775"

    - name: Seed shared content
      copy:
        dest: "{{ nfs_export_path }}/index.html"
        content: |
          <html>
            <body>
              <h1>Shared content from NFS</h1>
              <p>Served by web nodes through nginx.</p>
            </body>
          </html>
        mode: "0644"

    - name: Configure NFS exports
      copy:
        dest: /etc/exports
        content: |
          {{ nfs_export_path }} *(rw,sync,no_subtree_check,no_root_squash)
        mode: "0644"
      notify: Restart NFS

    - name: Ensure NFS service is enabled and running
      service:
        name: nfs-kernel-server
        state: started
        enabled: true

    - name: Export NFS shares
      command: exportfs -ra
      changed_when: false

  handlers:
    - name: Restart NFS
      service:
        name: nfs-kernel-server
        state: restarted
```

> Note: for stricter security, replace `*` in `/etc/exports` with your internal CIDR or specific web server IPs.

## `ansible/lb.yml`

```yaml
---
- name: Configure load balancer
  hosts: lb
  become: true
  vars:
    upstream_servers: "{{ groups['web'] | map('extract', hostvars, 'private_ip') | list }}"
  tasks:
    - name: Install nginx
      apt:
        name: nginx
        state: present
        update_cache: true

    - name: Configure nginx as reverse proxy with round-robin
      copy:
        dest: /etc/nginx/sites-available/default
        mode: "0644"
        content: |
          upstream backend {
          {% for ip in upstream_servers %}
              server {{ ip }}:80;
          {% endfor %}
          }

          server {
              listen 8082 default_server;
              listen [::]:8082 default_server;

              location / {
                  proxy_pass http://backend;
                  proxy_set_header Host $host;
                  proxy_set_header X-Real-IP $remote_addr;
                  proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
                  proxy_set_header X-Forwarded-Proto $scheme;
              }
          }
      notify: Restart nginx

# 4) Explanation

## Storage architecture: volume + NFS

The storage design uses:

- **One OpenStack block storage volume**
- Attached to:
  - **One NFS server**
- Exported via:
  - **NFS shared directory**
- Mounted by:
  - **Two web servers**

### How it works
1. Terraform provisions a block storage volume.
2. Terraform attaches the volume to the NFS VM.
3. Ansible formats the attached device and mounts it on the NFS server.
4. Ansible exports a shared directory from that mounted filesystem using NFS.
5. The web servers mount that exported directory at the nginx web root.
6. Both web servers therefore serve the **same shared content**.

### Why this approach
- The block volume provides **persistent storage** independent of the VM lifecycle.
- NFS allows multiple web nodes to access the same files concurrently.
- This is a straightforward design for small to medium shared-content web applications.

### Traffic flow
- Clients access the **load balancer** on port `8082`.
- The load balancer forwards requests in **round-robin** fashion to the two web servers on port `80`.
- The web servers serve content from the **NFS-mounted shared directory**.

## CI/CD workflow

The GitLab pipeline performs Terraform automation in two stages:

### 1. Validate stage
Runs:
- `terraform init`
- `terraform validate`

Purpose:
- Download providers and initialize backend
- Validate syntax and configuration consistency before deployment

### 2. Apply stage
Runs:
- `terraform init`
- `terraform apply -auto-approve`

Purpose:
- Provision or update infrastructure in OpenStack automatically from the default branch

### Security in CI/CD
- No credentials are stored in code
- OpenStack auth values are passed via GitLab CI variables
- Backend credentials are also injected via CI variables
- This keeps secrets out of version control

### Practical note
If you also want Ansible execution in the same pipeline, you can add another stage after `apply` to:
- install Ansible
- consume the generated inventory
- run `ansible-playbook site.yml`

Your task only explicitly required Terraform execution in CI, so the provided pipeline focuses on Terraform.

## Terraform state management approach

The solution uses a **remote HTTP backend**:

```hcl
terraform {
  backend "http" {}
}
```

### Why remote state
Remote state is preferred over local state because it:
- centralizes Terraform state
- avoids state loss in ephemeral CI runners
- improves team collaboration
- allows state locking to reduce concurrent modification issues

### Backend configuration
The actual backend endpoints are passed at runtime:

- `address`
- `lock_address`
- `unlock_address`
- `username`
- `password`

This means:
- backend details are not hardcoded
- credentials remain outside the repository
- the same code can be reused across environments

### State locking
The CI example includes:
- `lock_method=POST`
- `unlock_method=DELETE`

This helps prevent simultaneous pipeline jobs from corrupting state.

# Notes and recommendations

## 1. Security group default rules
Because OpenStack may auto-create default egress rules, the configuration sets:

```hcl
delete_default_rules = true
```

Then explicit egress rules are created so Terraform fully manages the security groups.

## 2. NFS exports hardening
For stronger security, instead of:

```text
/srv/nfs/shared *(rw,sync,no_subtree_check,no_root_squash)
```

use:
- the internal subnet CIDR, or
- the exact private IPs of web servers

Example:

```text
/srv/nfs/shared 10.10.0.0/24(rw,sync,no_subtree_check)
```

## 3. Access model
This example assigns floating IPs to:
- load balancer
- NFS server
- web servers

That simplifies Ansible connectivity. In a stricter production setup, you may instead:
- expose only the load balancer publicly
- use a bastion host for Ansible access to internal nodes

## 4. Applying Ansible
Terraform renders the inventory file, but does not directly execute Ansible. That separation is often preferable:
- Terraform handles infrastructure
- Ansible handles in-guest configuration
