## `playbooks/nfs.yml`

```yaml
- name: Configure NFS server
  hosts: nfs
  become: true
  tasks:
    - name: Install NFS and filesystem packages
      package:
        name:
          - nfs-utils
          - xfsprogs
          - e2fsprogs
        state: present

    - name: Create filesystem on attached volume
      filesystem:
        fstype: "{{ nfs_filesystem }}"
        dev: "{{ nfs_device }}"

    - name: Create mount point for attached volume
      file:
        path: "{{ nfs_export_dir }}"
        state: directory
        mode: "0777"

    - name: Mount attached volume
      mount:
        path: "{{ nfs_export_dir }}"
        src: "{{ nfs_device }}"
        fstype: "{{ nfs_filesystem }}"
        opts: defaults
        state: mounted

    - name: Deploy exports file
      template:
        src: ../templates/exports.j2
        dest: /etc/exports
        owner: root
        group: root
        mode: "0644"

    - name: Enable and start NFS service
      service:
        name: nfs-server
        state: started
        enabled: true

    - name: Reload exports
      command: exportfs -ra

    - name: Create test content
      copy:
        dest: "{{ nfs_export_dir }}/index.html"
        content: |
          <html>
          <body>
            <h1>Shared content from NFS server</h1>
          </body>
          </html>
        mode: "0644"
```

## `.gitlab-ci.yml`

This pipeline:

- runs `terraform init`
- runs `terraform validate`
- runs `terraform plan`
- runs `terraform apply`

It also uses a remote S3 backend configured from CI variables.

```yaml
image:
  name: hashicorp/terraform:1.6.6
  entrypoint: [""]

stages:
  - validate
  - plan
  - apply

variables:
  TF_ROOT: "infra"
  TF_IN_AUTOMATION: "true"
  TF_INPUT: "false"

before_script:
  - cd "$TF_ROOT"

validate:
  stage: validate
  script:
    - terraform init
      -backend-config="bucket=${TF_STATE_BUCKET}"
      -backend-config="key=${TF_STATE_KEY}"
      -backend-config="region=${TF_STATE_REGION}"
      -backend-config="encrypt=true"
    - terraform fmt -check
    - terraform validate
  rules:
    - if: '$CI_COMMIT_BRANCH'

plan:
  stage: plan
  script:
    - terraform init
      -backend-config="bucket=${TF_STATE_BUCKET}"
      -backend-config="key=${TF_STATE_KEY}"
      -backend-config="region=${TF_STATE_REGION}"
      -backend-config="encrypt=true"
    - terraform plan -out=tfplan
  artifacts:
    paths:
      - infra/tfplan
    expire_in: 1 hour
  rules:
    - if: '$CI_COMMIT_BRANCH'

apply:
  stage: apply
  script:
    - terraform init
      -backend-config="bucket=${TF_STATE_BUCKET}"
      -backend-config="key=${TF_STATE_KEY}"
      -backend-config="region=${TF_STATE_REGION}"
      -backend-config="encrypt=true"
    - terraform apply -auto-approve tfplan
  dependencies:
    - plan
  when: manual
  rules:
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'
```

# 5. Explanation

## Storage architecture: volume + NFS

The persistent storage design is:

1. **EBS volume**
   - Terraform provisions an `aws_ebs_volume`.
   - That volume is attached only to the NFS server.
   - This provides block storage persistence independent of the EC2 instance lifecycle.

2. **NFS server**
   - The NFS server formats and mounts the attached EBS volume.
   - It exports a shared directory, for example `/srv/nfs/shared`.

3. **Web servers**
   - Both web servers mount the exported NFS path over the network.
   - nginx on each web server serves content directly from the mounted shared directory.

### Why this works
- The EBS volume gives persistent storage.
- NFS makes the same shared files available to multiple web servers.
- Both web nodes serve identical content from one shared backend.

### Tradeoffs
- This is simple and fits the requirement well.
- It introduces a single point of failure at the NFS server.
- For production, managed shared storage services or multi-AZ file systems are usually better.

## CI/CD workflow

The GitLab pipeline follows a standard IaC workflow:

1. **Validate stage**
   - Runs `terraform init`
   - Runs `terraform fmt -check`
   - Runs `terraform validate`

2. **Plan stage**
   - Initializes Terraform again against the remote backend
   - Creates an execution plan with `terraform plan -out=tfplan`
   - Stores the plan as a pipeline artifact

3. **Apply stage**
   - Uses the generated plan artifact
   - Executes `terraform apply tfplan`
   - Marked as `manual` so a human reviews before deployment

### Why this is best practice
- Infrastructure changes are version controlled
- Validation catches syntax and schema issues early
- Plan provides a reviewable preview of changes
- Manual approval reduces accidental changes in shared environments

This aligns well with GitOps/IaC best practices: reviewed, repeatable, auditable changes.

## Terraform state management approach

This solution uses a **remote backend** in S3:

- State is not stored locally in CI runners
- All pipeline runs use the same centralized state location
- Teams can collaborate safely with shared infrastructure state

### Benefits
- Centralized source of truth
- Better collaboration
- Durable storage
- Easier automation in CI/CD

### Important note
For production AWS backends, add state locking. Traditionally this is done with DynamoDB locking, depending on your Terraform/OpenTofu version and backend pattern. If using S3 backend with locking support in your environment, enable it. The key point is:

- remote state in S3
- locking enabled where supported
- backend config injected via CI variables, not committed to repo

### Security
- No credentials are hardcoded
- Sensitive values stay in GitLab CI/CD variables or secret manager
- Backend configuration is provided at runtime

# 6. Notes and practical improvements

A few practical considerations:

1. **Private instances need connectivity for package install**
   - In this example, web and NFS instances are in a private subnet.
   - They will need NAT, SSM, internal package mirrors, or another egress path to install packages.
   - If you want fully working package installation from the internet, add a NAT gateway and private route table.

2. **Ansible execution**
   - Terraform provisions infrastructure only.
   - Ansible should run after Terraform, typically from:
     - a GitLab job
     - a bastion
     - AWX/Ansible Automation Platform
   - You can derive inventory from Terraform outputs.

3. **Provisioners**
   - I did not use Terraform provisioners for configuration management.
   - That is intentional and follows Terraform best practice: use Ansible for post-provision host setup.

4. **Load balancer choice**
   - Your requirement says “one load balancer.”
   - Here it is an EC2 instance running nginx as a round-robin reverse proxy.
   - If you wanted a managed load balancer instead, AWS ALB could be used, but that would change the design semantics.
