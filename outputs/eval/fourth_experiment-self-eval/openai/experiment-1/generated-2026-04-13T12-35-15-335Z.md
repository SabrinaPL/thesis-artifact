# Review of the original solution

The original submission was a strong start, but it had several issues:

## What was good
- Used variables instead of hardcoding most values
- Used remote backend pattern for Terraform
- Provisioned the required components:
  - 2 web servers
  - 1 load balancer
  - 1 NFS server
  - 1 persistent volume
- Used Ansible for configuration instead of Terraform provisioners
- Explained architecture and CI/CD clearly

## Issues that needed improvement
1. **Private subnet instances had no outbound internet path**
   - Web and NFS servers were in a private subnet, but there was no NAT gateway or other egress.
   - That means package installation via Ansible would fail.

2. **Security group design could be tighter**
   - Load balancer should be the main HTTP entry point.
   - Web servers should accept HTTP from the load balancer security group, not the whole VPC CIDR.
   - NFS security group should allow only required NFS-related ports from web servers.

3. **Unnecessary Terraform data source**
   - `data "aws_internet_gateway" "existing"` was not needed.

4. **Ansible NFS setup needed more care**
   - Filesystem creation should avoid reformatting an already formatted disk.
   - NFS-related services differ slightly by distro, so package/service assumptions should be documented.
   - Mount persistence and service restart behavior could be improved.

5. **CI pipeline should include formatting check explicitly**
   - Retrieved best practices mention `terraform fmt` and `terraform validate`.
   - The original included `fmt -check`, which is good, but we can organize pipeline stages more cleanly.

6. **Remote state locking should be explicit**
   - For AWS S3 backend, DynamoDB locking is the common safe pattern.
   - Since the task asked for remote backend, I retained S3 and documented lock table usage.

## `ansible/playbooks/nfs.yml`

```yaml
- name: Configure NFS server
  hosts: nfs
  become: true

  handlers:
    - name: restart nfs
      service:
        name: nfs-server
        state: restarted

    - name: reload exports
      command: exportfs -ra
      changed_when: true

  tasks:
    - name: Install NFS server and filesystem tools
      package:
        name:
          - nfs-utils
          - e2fsprogs
        state: present

    # The filesystem module is idempotent for common cases,
    # but in production you should be extra careful with disk formatting operations.
    - name: Create filesystem on attached EBS volume
      filesystem:
        fstype: "{{ nfs_filesystem }}"
        dev: "{{ nfs_device }}"

    - name: Create export directory
      file:
        path: "{{ nfs_export_dir }}"
        state: directory
        owner: root
        group: root
        mode: "0755"

    - name: Mount attached volume and persist in fstab
      mount:
        path: "{{ nfs_export_dir }}"
        src: "{{ nfs_device }}"
        fstype: "{{ nfs_filesystem }}"
        opts: defaults
        state: mounted

    - name: Configure NFS exports
      template:
        src: ../templates/exports.j2
        dest: /etc/exports
        owner: root
        group: root
        mode: "0644"
      notify:
        - reload exports
        - restart nfs

    - name: Enable and start NFS service
      service:
        name: nfs-server
        state: started
        enabled: true

    - name: Create shared demo content
      copy:
        dest: "{{ nfs_export_dir }}/index.html"
        content: |
          <html>
          <body>
            <h1>Shared content from NFS-backed storage</h1>
          </body>
          </html>
        owner: root
        group: root
        mode: "0644"
```

# Explanation

## 1. Storage architecture: volume + NFS

This design uses two storage layers:

### Layer 1: EBS volume
Terraform creates an **EBS volume** and attaches it to the NFS server.

- EBS is block storage
- it persists independently of the EC2 instance
- it is mounted on the NFS server as a filesystem

### Layer 2: NFS share
The NFS server exports a directory from that mounted EBS-backed filesystem.

- the NFS server acts as the shared storage gateway
- both web servers mount the same exported directory
- nginx on both web servers serves content directly from that shared mount

### Why this meets the requirement
- there is one persistent storage volume
- that volume is attached to the NFS server
- both web servers consume the same shared storage over NFS

### Important tradeoff
This is simple and works well for a learning/demo environment, but the NFS server is a **single point of failure**. In production, a managed shared filesystem such as AWS EFS is often preferable.

---

## 2. CI/CD workflow

The GitLab pipeline follows a clean Terraform workflow:

### `fmt`
Runs:

```sh
terraform fmt -check -recursive
```

This ensures code formatting is consistent. Consistency improves maintainability and readability.

### `validate`
Runs:

```sh
terraform validate
```

This checks Terraform syntax and internal consistency before planning changes.

### `plan`
Runs:

```sh
terraform plan -out=tfplan
```

This creates an execution plan and stores it as an artifact. Teams can review this before applying infrastructure changes.

### `apply`
Runs:

```sh
terraform apply -auto-approve tfplan
```

This applies the previously reviewed plan. It is marked **manual** and restricted to the default branch, which is safer for shared environments.

---

## 3. Terraform state management approach

This solution uses a **remote S3 backend** for Terraform state.

### Why remote state is important
Terraform state records what resources exist and how Terraform maps them.

If state is stored only on a local laptop or ephemeral CI runner:
- teammates cannot collaborate reliably
- pipelines may drift from real infrastructure
- state can be lost

### Remote backend used here
The backend is configured at runtime through GitLab CI variables:

- `TF_STATE_BUCKET`
- `TF_STATE_KEY`
- `TF_STATE_REGION`
- `TF_LOCK_TABLE`

### Why not hardcode backend values
Because backend values are environment-specific and should not be embedded in source code. This makes the same code reusable for dev, test, and prod.

### Locking
A DynamoDB lock table is included in the CI init command. Locking prevents two Terraform runs from modifying the same state at the same time.

That matters because concurrent state writes can corrupt infrastructure management.

# Improvements made and rationale

## 1. Added NAT gateway for private subnet egress
**Problem fixed:** web and NFS instances in the private subnet could not install packages.

**Why it matters:** without outbound connectivity, Ansible package installation fails.

**Improvement:** added:
- Elastic IP
- NAT gateway
- private route table
- route table association

This makes the design functionally complete.

## 2. Tightened web server HTTP access
**Problem fixed:** web servers originally allowed port 80 from the entire VPC CIDR.

**Why it matters:** only the load balancer should send application traffic to web servers.

**Improvement:** changed web server ingress on port 80 to allow traffic only from the **load balancer security group**.

This reduces lateral exposure and follows least privilege.

**Problem fixed:** unused `data "aws_internet_gateway"` block.
